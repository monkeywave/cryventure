## Two hashes, two pads

Bellare, Canetti and Krawczyk introduced HMAC with a proof (CRYPTO 1996); RFC 2104 (1997)
specified it, and NIST adopted it as FIPS 198 (2002), now FIPS 198-1 (2008). It wraps any iterated
hash `H` with block size `B` and output size `L` (RFC 2104, §2):

<Formula caption="HMAC, RFC 2104 §2 and FIPS 198-1 §4. K0 = the key as one B-byte block.">
{`HMAC(K, m) = H( (K0 ⊕ opad) ‖ H( (K0 ⊕ ipad) ‖ m ) )
ipad = 36 36 … 36   (B bytes)
opad = 5c 5c … 5c   (B bytes)`}
</Formula>

<KeyFacts>
  <KeyFact label="SHA-256 block B" value="64 bytes" kind="state" />
  <KeyFact label="SHA-256 output L" value="32 bytes" kind="ciphertext" />
  <KeyFact label="ipad / opad" value="0x36 / 0x5c" kind="constant" />
  <KeyFact label="Hash calls" value="2, nested" kind="constant" />
</KeyFacts>

<WhyBox constant="ipad = 0x36, opad = 0x5c" title="why these two pads">
  HMAC is NMAC with two keys derived as `f(K0 ⊕ ipad)` and `f(K0 ⊕ opad)`; the proof treats them as
  independent, which needs different pads (BCK 1996, §5.2; RFC 2104, §2). BCK chose `0x36` and
  `0x5c` for a simple representation and a high Hamming distance: `36 ⊕ 5c = 6a = 01101010`, 4 of
  8 bits per byte. Nothing deeper is claimed.
</WhyBox>

<WhyBox constant="t ≥ 80 bits" title="why a tag needs at least 80 bits">
  RFC 2104, §5 asks for at least `L/2` and at least 80 bits, a suitable lower bound on the bits an
  attacker must predict.
</WhyBox>

<Lens only="story">

The message is sealed in an inner envelope, and that envelope in an outer one with a second seal.

</Lens>

## RFC 4231, test case 1

The key is 20 bytes of `0b`, the message `"Hi There"` (RFC 4231, §4.2). The derivation view draws
the whole chain: `K` → `K0` (padded with 44 zero bytes to `B = 64`) → `K0 ⊕ ipad` and `K0 ⊕ opad`
→ inner hash → tag. Byte 0: `0b ⊕ 36 = 3d`, `0b ⊕ 5c = 57`.

The last step outputs the RFC's HMAC-SHA-256 tag

`b0344c61d8db38535ca8afceaf0bf12b881dc200c9833da726e9376c2e32cff7`.

The inner and outer nodes link to the SHA-256 lab with their exact input. This lab is a teaching
tool: never type a real key into it.

## Key block, midstates, truncation

FIPS 198-1, §4 (steps 1–3) turns `K` into `K0`:

| Key length | K0 |
|---|---|
| = B | `K` |
| < B | `K ‖ 00 … 00` |
| > B | `H(K) ‖ 00 … 00` |

RFC 4231 test case 6 (§4.7) has a 131-byte key, so `K0 = SHA-256(K) ‖ 00 … 00` with
`SHA-256(K) = 45ad4b37 … a521db81`; the tag is `60e43159 … 0ee37f54`.

<Lab labId="hmac-long-key" producerId="hmac" presetId="rfc4231-tc6-longkey" startAt="op:keyPrep" layout="derivation:45|state:30|narration:25" />

The blocks `K0 ⊕ ipad` and `K0 ⊕ opad` depend only on the key. RFC 2104, §4 stores the two
**midstates** after them; each message then costs its own blocks plus one outer compression.

A tag may be **truncated** to its leftmost `t` bits (FIPS 198-1, §5), with `t ≥ L/2` and
`t ≥ 80` (RFC 2104, §5); RFC 4231 test case 5 keeps 128 bits (§4.6). For SHA-3, `B` is the rate:
136 bytes for SHA3-256 (FIPS 202, §7, Table 3).

<Lens level="cryptographer">

HMAC is NMAC with two keys derived from one (BCK 1996). Bellare (CRYPTO 2006) proves it a PRF if
the compression function is one, without collision resistance.

</Lens>

</LessonSection>

## Two midstates per key

For SHA-256 each midstate is a 32-byte chaining value; the state view shows both, as
`Inner midstate` and `Outer midstate`. A server that verifies many messages under one key keeps
these 64 bytes instead of `K` (RFC 2104, §4).

They are as valuable as the key: with both midstates anyone can compute tags for any message, which
is why RFC 2104, §4 asks to protect them like `K`. The lab marks `K`, `K0`, the padded keys and the
midstates as secret values; the message and the tag as public.

All hashing in HMAC runs the hash's compression function, so SHA-NI and the ARMv8 SHA2
instructions apply unchanged ([SHA-256 page](../../hash/sha256/)).

</LessonSection>

## Mallory reads the clock

**No outer hash.** HMAC would shrink to `H((K0 ⊕ ipad) ‖ m)`, a secret-prefix MAC open to length
extension ([SHA-512 page](../../hash/sha512/#mallory-extends-the-chain)).

**Short tags.** Fewer bits mean fewer to predict; RFC 2104, §5 keeps at least 80.

**Early-exit comparison.** In 2009 Nate Lawson reported that Google's Keyczar library compared HMAC
tags byte by byte and returned at the first difference, so the verification time revealed how many
leading bytes of a forged tag were right (Lawson 2009). The fix is a comparison whose time does not
depend on the data: the lab's verify step XORs every byte pair and ORs the result into an
accumulator without exiting early. Libraries ship such a function, e.g. Python's
`hmac.compare_digest` (Python docs).

## Check yourself

<CheckQuestion
  id="hmac-pads-must-differ"
  number={1}
  question="What does the HMAC security proof need from ipad and opad?"
  options={[
    'They must be prime numbers',
    'They must differ, so the inner and outer hash use different keys',
    'They must be each other’s bitwise complement',
    'They must be secret',
  ]}
  answer={1}
>
  That they differ, so the two derived keys can be treated as independent (Bellare, Canetti,
  Krawczyk 1996, §5.2; RFC 2104, §2). `0x36` and `0x5c` are public, fixed for interoperability, and
  differ in 4 of 8 bits per byte.
</CheckQuestion>

<CheckQuestion
  id="hmac-long-key-k0"
  number={2}
  question="HMAC-SHA-256 gets a 131-byte key. What is K0?"
  options={[

    'The key XORed with ipad',

  answer={1}
>
  A key longer than `B = 64` bytes is hashed first, then zero bytes fill `K0` up to `B` (FIPS 198-1,
  §4, step 2; RFC 4231, §4.7).
</CheckQuestion>
