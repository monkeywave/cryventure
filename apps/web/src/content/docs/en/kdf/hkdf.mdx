## One secret in, many keys out

A **key derivation function** (KDF) turns secret material, such as a Diffie-Hellman shared secret,
into the keys a protocol uses (RFC 5869, §1). HKDF has two [HMAC](../../mac/hmac/)-based halves,
**extract-then-expand** (Krawczyk, CRYPTO 2010; RFC 5869, §1):

<KeyFacts>
  <KeyFact label="Extract" value="PRK = HMAC(salt, IKM)" kind="key" />
  <KeyFact label="Expand" value="OKM, L bytes" kind="ciphertext" />
  <KeyFact label="Max. L" value="255 · HashLen" kind="constant" />
</KeyFacts>

**Extract** condenses unevenly random input keying material (IKM) into a pseudorandom key,
PRK (§2.2). **Expand** stretches PRK into as much output keying
material (OKM) as needed, bound to a context string `info` (§2.3).

<WhyBox constant="255 · HashLen" title="why the output is capped">
  Expand numbers its blocks with a single counter octet, `0x01` … `0xff`, so at most 255 blocks of
  HashLen bytes exist: 8160 bytes for SHA-256 (RFC 5869, §2.3).
</WhyBox>

## Extract, then expand

<Formula caption="HKDF, RFC 5869 §2.2 and §2.3 (‖ = concatenation, N = ⌈L / HashLen⌉).">
{`PRK  = HMAC-Hash(salt, IKM)
T(0) = empty string
T(i) = HMAC-Hash(PRK, T(i−1) ‖ info ‖ i)      i = 0x01 … N
OKM  = first L octets of T(1) ‖ T(2) ‖ … ‖ T(N)`}
</Formula>

The **salt** is optional: if it is empty, Extract uses HashLen zero bytes (§2.2). A random salt
"adds significantly to the strength of HKDF" and need not be secret (§3.1). **Info** binds each
key to its purpose: different info, independent keys from the same PRK (§3.2). Test case A.3 has
neither:

`Derive-Secret` passes a transcript hash as the context. The lab reproduces RFC 8448 (§3):

## Midstates and short-lived secrets

PRK is the HMAC key of every Expand block. HMAC's inner and outer hashes start by absorbing
`K0 ⊕ ipad` and `K0 ⊕ opad`, so an implementation can store those two intermediate states once per
key (RFC 2104, §4). In test case A.1 each `T(i)` input is at most 32 + 10 + 1 = 43 bytes, so every
block then costs two SHA-256 compressions.

| Value | Size (A.1) | Secret? |
|---|---|---|
| IKM | 22 bytes | yes |
| salt, info | 13, 10 bytes | no (RFC 5869, §3.1, §3.2) |
| PRK | HashLen = 32 bytes | yes |
| OKM | L = 42 bytes | yes |

RFC 8446 (§7.1) recommends (SHOULD) that a secret be erased once every value derived from it is computed. How long
such keys linger in a process's memory is the topic of a later phase.

</LessonSection>

## Mallory's shortcuts

**Skip Extract.** RFC 5869 allows it only when IKM is already a uniformly random key; a
Diffie-Hellman value is not, and Extract is what makes it one (§3.3).

**Drop info.** Two keys from the same PRK with the same info and L are identical. If an encryption
key and a MAC key come out equal, the two uses are no longer independent; distinct info strings
keep them apart (§3.2).

**Feed it a password.** Extract "can concentrate existing entropy but cannot amplify entropy", and
HKDF has no mechanism to slow down a dictionary attack (§4). Each of Mallory's password guesses
costs only a few HMAC calls. Passwords need a deliberately slow KDF such as
[PBKDF2](../pbkdf2/) (RFC 5869, §4 points to PKCS #5).

<Lens level="engineer">

Asking for L > 255 · HashLen is an error, not a longer key (RFC 5869, §2.3).

</Lens>

## Check yourself

<CheckQuestion
  id="hkdf-empty-salt"
  number={1}
  question="What does HKDF-Extract use as the HMAC key when the salt is empty?"
  options={[
    'The IKM itself',
    'HashLen zero bytes',
    'A random value chosen by the library',
    'Extract is skipped',
  ]}
  answer={1}
>
  RFC 5869, §2.2: if the salt is not provided, it is set to a string of HashLen zeros. Test case A.3
  shows the result: PRK `19ef24a3 … 293ccb04`.
</CheckQuestion>

<CheckQuestion
  id="hkdf-max-length"
  number={2}
  question="What is the longest OKM that HKDF-SHA-256 can produce?"
  options={['32 bytes', '255 bytes', '8160 bytes', 'Unlimited']}
  answer={2}
>
  L ≤ 255 · HashLen (RFC 5869, §2.3), because the block counter is one octet: 255 · 32 = 8160
  bytes.
</CheckQuestion>

<CheckQuestion
  id="hkdf-not-for-passwords"
  number={3}
  question="Why is HKDF the wrong choice for deriving a key from a password?"
  options={[
    'HMAC cannot take a password as input',
    'It needs a secret salt',
    'It cannot add entropy and does not slow down guessing',
    'Its output is too short',
  ]}
  answer={2}
>
  Extract only concentrates the entropy that is there, and HKDF has no work factor against
  dictionary attacks (RFC 5869, §4). Use a password-based KDF such as [PBKDF2](../pbkdf2/).
</CheckQuestion>
