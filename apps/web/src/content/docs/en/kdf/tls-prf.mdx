## One secret in, any number of bytes out

A TLS 1.0–1.2 handshake ends with a **pre-master secret**. The PRF turns it into the 48-byte
**master secret**, keyed to both hello randoms, and the master secret into the **key block** that
holds the session's MAC keys, cipher keys and IVs (RFC 5246 §8.1, §6.3; RFC 2246 §8.1, §6.3).

The PRF takes a secret, an ASCII **label** and a **seed**, and expands them with
[HMAC](../../mac/hmac/) to as many bytes as asked for (RFC 5246 §5). The label names the use:
"master secret" (§8.1) or "key expansion" (§6.3), so the two outputs come from different inputs.

  <KeyFact label="Master secret" value="48 bytes" kind="key" />
  <KeyFact label="TLS 1.0/1.1" value="P_MD5 ⊕ P_SHA-1" kind="constant" />
  <KeyFact label="TLS 1.2" value="P_SHA256" kind="constant" />
  <KeyFact label="TLS 1.3" value="HKDF" kind="constant" />
</KeyFacts>

<WhyBox constant="48" title="why the master secret is 48 bytes">
  RFC 5246 §8.1 fixes it: `PRF(pre_master_secret, "master secret", ClientHello.random +
  ServerHello.random)[0..47]`, "always exactly 48 bytes", whatever the key exchange produced.
</WhyBox>

<Lens only="story">

A recipe that stirs one shared secret into as many fresh keys as the conversation needs.

## The A(i) chain

<Formula caption="P_hash, RFC 5246 §5 (+ = concatenation). TLS 1.2: PRF = P_SHA256(secret, label + seed).">
{`A(0) = label + seed
A(i) = HMAC_hash(secret, A(i−1))
P_hash(secret, label + seed) = HMAC_hash(secret, A(1) + label + seed) +
                               HMAC_hash(secret, A(2) + label + seed) + …`}
</Formula>

The chain `A(i)` only feeds the blocks; every output block also hashes the seed again. P_hash runs
as often as needed and drops the surplus (RFC 5246 §5).

<Formula caption="TLS 1.0/1.1 PRF, RFC 2246 §5 (unchanged in RFC 4346 §5).">
{`S1 = first ⌈|secret| / 2⌉ bytes      S2 = last ⌈|secret| / 2⌉ bytes
PRF(secret, label, seed) = P_MD5(S1, label + seed) ⊕ P_SHA-1(S2, label + seed)`}
</Formula>

For an odd length, S1's last byte is S2's first (RFC 2246 §5). TLS 1.2 drops the split and uses
one hash: SHA-256 for all suites of RFC 5246, and new suites must name their PRF (RFC 5246 §5);
the `*_SHA384` suites, e.g. of RFC 5288 and RFC 5289, use `P_SHA384` (RFC 5288 §3; RFC 5289 §3).

<Lens level="cryptographer">

RFC 2246 §5 calls the XOR a hedge: it "should guarantee its security if either algorithm remains
secure". Each half is keyed with only half of the secret, though.

</Lens>

</LessonSection>

<LessonSection part="memory">

## What sits in memory

During the PRF, a TLS stack holds the secret as an HMAC key, the current `A(i)`, the label and seed,
and an output buffer. HMAC lets it hash the padded key once and keep the inner and outer keyed
states for every later call (RFC 2104 §4). Then `A(2)`, `A(3)`, … cost two compressions each.
`A(1)` and every output block also hash label + seed (77 bytes for the master secret), so they
cost three.

What survives the handshake is the 48-byte master secret: TLS 1.2 keeps it with the session so
that resumption can derive new keys from it (RFC 5246 §8.1, §7.3). Anyone who reads those 48 bytes
plus the public randoms can rerun the key-expansion PRF and decrypt the session.

<Lens level="engineer">

The key block uses `server_random + client_random`, the master secret `client_random +
server_random` (RFC 5246 §6.3, §8.1). Swapping them gives valid-looking, wrong keys.

</Lens>

</LessonSection>

<LessonSection part="break">

## History: the triple handshake

The TLS 1.2 master secret depends only on the pre-master secret and the two randoms (RFC 5246
§8.1). Bhargavan et al. (IEEE S&P 2014) showed that a malicious server can make two different
connections, one with the client and one with a real server, end with the **same** master secret.
Combined with session resumption and renegotiation, this broke the client authentication that
applications relied on (RFC 7627 §1). This page tells the history, not the attack steps.

The fix, RFC 7627, binds the master secret to the whole handshake:

<Formula caption="RFC 7627 §4; session_hash is the hash of the handshake messages from ClientHello up to and including ClientKeyExchange (§3).">
{`master_secret = PRF(pre_master_secret, "extended master secret", session_hash)[0..47]`}
</Formula>

TLS 1.3 replaced the PRF with [HKDF](../hkdf/) and hashes the transcript into its whole key
schedule (RFC 8446 §1.2, §7.1).

<Lens level="cryptographer">

P_hash itself did nothing wrong here: it was a sound PRF fed a seed that did not cover enough of the
handshake. RFC 7627 fixes the input, not the function (RFC 7627 §1, §4).

</Lens>

</LessonSection>

<CheckQuestion
  id="p-hash-a-chain"
  number={1}
  question="In P_hash, what is A(2)?"
  options={[
    'HMAC(secret, A(1) + seed)',
    'HMAC(secret, A(1))',
    'HMAC(A(1), secret)',
    'A(1) ⊕ seed',
  ]}
  answer={1}
>
  RFC 5246 §5: `A(i) = HMAC_hash(secret, A(i−1))`, with `A(0)` the label plus seed. The output
  blocks are `HMAC_hash(secret, A(i) + label + seed)`; the chain itself never sees the seed again.
</CheckQuestion>

<CheckQuestion
  id="tls10-prf-hedge"
  number={2}
  question="Why does the TLS 1.0 PRF XOR a P_MD5 and a P_SHA-1 output?"
  options={[
    'To make the PRF twice as fast',
    'So that it stays secure if either of the two hashes stays secure',
    'Because MD5 alone produces too few bytes',
    'To encrypt the master secret',
  ]}
  answer={1}
>
  RFC 2246 §5 uses two hash algorithms "in a way which should guarantee its security if either
  algorithm remains secure". TLS 1.2 dropped the hedge for a single, stronger hash (RFC 5246 §5).
</CheckQuestion>

<CheckQuestion
  id="extended-master-secret-seed"
  number={3}
  question="What does the RFC 7627 extended master secret use as its seed?"
  options={[
    'ClientHello.random + ServerHello.random',
    'ServerHello.random + ClientHello.random',

  answer={2}
>
  RFC 7627 §4 derives the master secret from `session_hash`, the hash of the handshake transcript
  (§3), so two different handshakes cannot end with the same master secret as in the triple
  handshake (Bhargavan et al., IEEE S&P 2014).
