## A block cipher is not yet a cipher for messages

AES encrypts exactly one 16-byte block. Real messages are longer, so we need a **mode of
operation**: a rule for applying the block cipher to many blocks. NIST SP 800-38A defines five of
them. The simplest is the **Electronic Codebook** mode, ECB (§6.1).

ECB cuts the message into blocks `P₁ … Pₙ` and encrypts each one on its own, always with the same
key. No block influences another.

<Formula caption="ECB encryption and decryption, NIST SP 800-38A §6.1.">
{`Cⱼ = E_K(Pⱼ)        for j = 1 … n
Pⱼ = D_K(Cⱼ)        for j = 1 … n`}
</Formula>

<Lens only="story">

Think of a giant codebook with one page per key: every possible 16-byte block has exactly one
fixed code word. Encrypting means looking up each block in the book. Whoever sees the same code
word twice knows the same block was sent twice.

</Lens>

</LessonSection>

## Block by block, no memory

1. **Pad** the plaintext to a whole number of blocks (see Part 4).
2. **Split** it into 16-byte blocks `P₁ … Pₙ`.
3. **Encrypt** each block with the forward cipher: `Cⱼ = E_K(Pⱼ)`. The order does not matter, so
   all blocks can run in parallel, for encryption and decryption alike (SP 800-38A §6.1).

ECB has no IV and no counter. It is **deterministic**: under one key, a given plaintext block
always becomes the same ciphertext block. SP 800-38A §6.1 says so itself: if that is undesirable,
do not use ECB.

In the lab, both `41545441434b204154204441574e2121` blocks encrypt to
`541ff0c92b9251ae06c624c4a8ab2a85`.

<Lens level="cryptographer">

Any deterministic scheme fails IND-CPA: the attacker asks the encryption oracle for `E(m₀)`, then
submits `m₀, m₁` as the challenge and compares. ECB fails even within one message, because equal
blocks repeat. It also lets an attacker **reorder, drop or splice** whole ciphertext blocks without
any error on decryption.

</Lens>

</LessonSection>

<LessonSection part="memory">

## What ECB ciphertext looks like

The ciphertext is just `C₁ ‖ C₂ ‖ … ‖ Cₙ`: block `j` starts at byte `16·(j − 1)`, with no header,
IV or tag.

ECB needs whole blocks. SP 800-38A leaves padding to the application (Appendix A); a common
choice is **PKCS#7** (RFC 5652, §6.3): append `k − (len mod k)` bytes, each with that value, where
`k` is the block size. So between 1 and 16 bytes are always added.

<WhyBox constant="0x10" title="a full block of padding">
  Our 32-byte message already fills two blocks, yet RFC 5652 §6.3 still appends 16 bytes of `10`
  (= 16). Padding is never empty, so the receiver can always read the last byte and strip that many. That is the third block `a254be88…` in the lab.
</WhyBox>

A bit error in `Cⱼ` garbles only `Pⱼ`; the other blocks decrypt correctly (SP 800-38A, Appendix D).

</LessonSection>

## Mallory looks at the penguin

An image is a long run of pixel bytes. Flat colour areas produce many identical 16-byte blocks,
and ECB turns them into identical ciphertext blocks. The colours become noise, but the **edges**
between areas stay put: the outline survives encryption.

This is the classic "ECB penguin", an illustration that has circulated in cryptography teaching for
two decades. Our penguin is original artwork, encrypted live in your browser with AES. Switch to
CBC (next lesson) and the picture turns into uniform noise.

<Lens level="engineer">

Upload your own picture: photos with gradients leak less than logos or screenshots, but any
repeated block is visible. Never use ECB for more than a single block of random data.

</Lens>
