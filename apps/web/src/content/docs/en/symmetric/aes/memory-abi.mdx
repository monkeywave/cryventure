## One struct, three byte patterns

OpenSSL keeps an expanded AES key in `AES_KEY`: 60 32-bit words `rd_key` plus an `int rounds`
(`include/openssl/aes.h:36–43`, OpenSSL 3.5.9). `AES_MAXNR` is 14 (`aes.h:33`), so `rd_key` always
has room for the 15 round keys of AES-256. On both targets of this lesson, `x86_64-linux-gnu` and
`aarch64-linux-gnu` (LP64, little-endian), clang 23.1.0 lays the struct out the same way:

<KeyFacts>
  <KeyFact label="sizeof(AES_KEY)" value="244 B · align 4" kind="key" />
  <KeyFact label="rd_key" value="offset 0 · 240 B" kind="key" />
  <KeyFact label="rounds" value="offset 240 · 4 B" kind="constant" />
</KeyFacts>

What lands *in* those bytes depends on the code that fills them:

| Implementation | Triples | `rd_key` bytes | `rounds` (128/192/256) |
|---|---|---|---|
| `c-ref` (`aes_core.c:3045`) | x86_64, aarch64 | host-endian 32-bit words | 10 / 12 / 14 |
| `aesni` (`aesni-x86_64.pl:4371`) | x86_64 | raw key bytes | 9 / 11 / 13 |
| `armv8` (`aesv8-armx.pl:127`) | aarch64 | raw key bytes | 10 / 12 / 14 |

<Lens only="story">

Think of `AES_KEY` as a shelf with 60 four-byte boxes. One implementation packs every box back to front;
the others pack them in reading order.

</Lens>

<Lens level="cryptographer">

With `AES_LONG` defined, `rd_key` would hold `unsigned long` (8 bytes on LP64): 488 bytes, align 8
(`aes.h:37–41`). No OpenSSL 3.5.9 configuration defines it.

</Lens>

## GETU32 versus a plain copy

The portable C key schedule reads every key word big-endian with `GETU32`
(`aes_local.h:26`: `pt[0]<<24 ^ pt[1]<<16 ^ pt[2]<<8 ^ pt[3]`) and stores it as a native `u32`
(`aes_core.c:3067`). A little-endian CPU writes the low byte first, so each 4-byte word appears
reversed in RAM. The AES-NI and ARMv8 schedules load the key into a 128-bit vector register and store
it unchanged (`aesni-x86_64.pl:4382, 4398`; `aesv8-armx.pl:162, 174`).

<Formula caption="AES_KEY bytes for FIPS 197 C.1, from the lab's memory facet.">
{`offset  field           c-ref          aesni          armv8
0       rd_key (w[0])   03 02 01 00    00 01 02 03    00 01 02 03
172     rd_key (w[43])  c5 30 2b 4d    4d 2b 30 c5    4d 2b 30 c5
240     rounds          0a 00 00 00    09 00 00 00    0a 00 00 00`}
</Formula>

<WhyBox constant="rounds" title="9, not 10">
  The AES-NI code uses the field as its `aesenc` loop count and then adds one `aesenclast`
  (`aesni-x86_64.pl:244–267, 282`); its own comments call it "rounds-1" (`:4304`). A schedule written by
  one implementation only fits that implementation's encrypt routine.
</WhyBox>

On x86_64, an OpenSSL build with assembly does not compile `aes_core.c` at all
(`build.info:10–14`), so `c-ref` there means a `no-asm` build. aarch64 compiles it as the C fallback
(`build.info:34–35`).

</LessonSection>

## A modeled stack frame

The lab models one function with three locals, `unsigned char in[16], out[16]; AES_KEY key;`, placed
below a frame base in declaration order, each on a 16-byte boundary. The addresses are **modeled**:
deterministic and typical for a Linux user stack, but not recorded from a real process. ASLR moves
the stack on every run, and compilers may reorder locals.

| Local | x86_64 | aarch64 | Bytes |
|---|---|---|---|
| `in` | `0x7ffc5e3a0ff0` | `0xffffd2c4eff0` | 16 |
| `out` | `0x7ffc5e3a0fe0` | `0xffffd2c4efe0` | 16 |
| `key` | `0x7ffc5e3a0ee0` | `0xffffd2c4eee0` | 244 |

AES-128 fills only the first 176 bytes of `rd_key` (11 round keys, FIPS 197 §5.2); `rounds` sits at
`key + 240`. Bytes 176–239 keep whatever was there before.

The fly-through follows round key 0 (or the ciphertext block bound for `out`) from the 4×4 matrix into the `xmm0` lanes
and on into RAM. Switch between the C reference and AES-NI to see the word reversal.

## Mallory reads a forgotten key

Round key 0 *is* the cipher key (FIPS 197, §5.2), so `AES_KEY` holds the key and the whole schedule.
If the struct goes out of scope without being wiped, those bytes stay in the stack or heap page until
something overwrites them. A core file, a swapped-out page or a memory dump can then hand Mallory the
key, and the schedule's structure makes it easy to find and even repair (Halderman et al., 2008).

A plain `memset` just before the struct dies is a dead store that the compiler may remove (CWE-14).
OpenSSL provides `OPENSSL_cleanse()`, which zeroes memory in a way the optimizer cannot drop
(OPENSSL_malloc(3)). Key lifetimes, zeroization and scanning real dumps are the topic of the later
**Secrets in memory** track.

</LessonSection>
