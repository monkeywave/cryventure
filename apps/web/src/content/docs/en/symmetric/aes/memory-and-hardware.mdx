## Same math, different cuts

Every fast implementation computes exactly the FIPS 197 rounds, but each one slices them
differently. CPUs bundle several steps into one instruction, and libraries pick a memory layout for
the expanded key. When you look at a debugger or a memory dump, you see these slices — not the
textbook picture.

This overview introduces both cuts. Two lessons go into detail:

- [AES_KEY in memory](../memory-abi/): the struct layout on x86_64 and aarch64 Linux, byte order
  and the `rounds` field.
- [AES-NI and ARMv8 instructions](../aes-ni/): real compiler output, step by step next to the
  registers.

</LessonSection>

## Two instruction sets

<Formula caption="AES-128 encryption with round keys k0 … k10.">
{`x86 AES-NI                      ARMv8 Crypto Extensions
PXOR       k0                   AESE  k0 … k8 ; AESMC  (rounds 1 … 9)
AESENC     k1 … k9              AESE  k9               (final round)
AESENCLAST k10                  EOR   k10`}
</Formula>

`AESENC` performs ShiftRows, SubBytes, MixColumns and *then* XORs the round key. `AESE` XORs the
round key *first*, then ShiftRows and SubBytes; `AESMC` is a separate MixColumns. Hence ARM needs a
plain `EOR` for the last key (Intel SDM Vol. 2A, AESENC; Arm ARM, AESE/AESMC). The
[instruction lesson](../aes-ni/) steps through both listings.

</LessonSection>

## OpenSSL's AES_KEY

<Formula caption="include/openssl/aes.h (AES_MAXNR = 14).">
{`struct aes_key_st {
    unsigned int rd_key[4 * (AES_MAXNR + 1)];  /* 60 × u32 = 240 bytes */
    int rounds;                                /* 10/12/14 (AES-NI: 9/11/13) */
};`}
</Formula>

The portable C code loads key bytes big-endian (`GETU32`) and stores each word as a **host-endian**
integer (`aes_core.c:3067`): on little-endian x86_64 and aarch64 the bytes of every word appear
reversed in memory. The AES-NI and ARMv8 code keeps the bytes in their natural order. The
[AES_KEY lesson](../memory-abi/) shows all four combinations.

</LessonSection>

## T-tables and the cache

Classic software AES merges SubBytes, ShiftRows and MixColumns into four 1 KiB lookup tables
(`Te0 … Te3`) indexed by secret bytes. Which cache lines get loaded depends on the key — Bernstein
(2005) and Osvik, Shamir and Tromer (2006) recovered keys from cache timing. **Constant-time**
code avoids secret-dependent lookups: hardware instructions, bitslicing, or vector-permute AES. The
[instruction lesson](../aes-ni/) tells the story in its Break part.

An expanded key that is never wiped stays in memory for anyone who can read it; the
[AES_KEY lesson](../memory-abi/) shows why a plain `memset` is not enough. Later labs will let you
scan a memory dump for an expanded key schedule and run a toy cache-timing attack against a T-table
implementation.

</LessonSection>
