## A state, not a chain

SHA-3 drops Merkle–Damgård. It keeps one **1600-bit state** and one permutation,
Keccak-f[1600] (FIPS 202, §3.1, §5.2). The state splits in two (§4):

- the **rate** `r`: the part the message is XORed into and the output is read from;
- the **capacity** `c = 1600 − r`: never touched by input, never output.

It **absorbs** the padded message `r` bits per permutation, then **squeezes** `r` bits per
permutation until it has enough output (§4, Algorithm 8).

<KeyFacts>
  <KeyFact label="State" value="1600 bit" kind="state" />
  <KeyFact label="SHA3-256 rate" value="1088 bit" kind="plaintext" />
  <KeyFact label="SHA3-256 capacity" value="512 bit" kind="key" />
  <KeyFact label="Rounds" value="24" kind="constant" />
</KeyFacts>

<WhyBox constant="c = 2d" title="why the capacity is twice the digest">
  FIPS 202, §6.1 sets `c = 2d` for every SHA-3 hash: SHA3-256 uses `c = 512`. Generic attacks on a
  sponge need about 2<sup>c/2</sup> work, so `c = 2d` matches the `d/2`-bit collision bound of a
  `d`-bit digest (Appendix A.1).
</WhyBox>

<Lens only="story">

A sponge soaks up water through its surface and keeps a wet core you never see. Squeeze it, and
water comes out of the surface only.

</Lens>

</LessonSection>

## "abc" through one permutation

This lab hashes "abc" with SHA3-256 and shows one step per permutation (FIPS 202, §4). The three
bytes plus padding fill one 136-byte rate block (§7, Table 3). Watch the phases: **pad**, **absorb**
into the rate lanes, **permute** all 1600 bits, **squeeze** the rate, keep the first 256 bits.

The digest is `3a985da7 4fe225b2 … 11431532` (NIST, SHA3-256 examples).

## Padding, domain bits and endless output

Each function first appends a **suffix** (FIPS 202, §6.1–6.2; SP 800-185, §3.3); **pad10\*1** then
adds `1`, zeros and a final `1` (§5.1). Bits fill bytes from the least significant end (Appendix
B.1), so suffix and first pad bit share one byte:

| Function | Suffix bits | First pad byte | Rate |
|---|---|---|---|
| SHA3-256 | `01` | `06` | 136 bytes |
| SHAKE128 | `1111` | `1f` | 168 bytes |
| cSHAKE128 (N or S set) | `00` | `04` | 168 bytes |
| Keccak-256 (original) | none | `01` | 136 bytes |

The last pad byte is `80`; for "abc" the block reads `61 62 63 06 00 … 00 80` (Appendix B.2).

SHAKE128 is an **XOF**: it squeezes as long as you like. Here 336 bytes take two rate blocks, with
a permutation before the second squeeze (§4, steps 8–10).

<Lab labId="shake128-abc-336" producerId="sha3" presetId="shake128-abc-336" layout="sponge:55|state:20|narration:25" />

**cSHAKE** adds a function name `N` and a customization string `S`, encoded into a full rate block
absorbed before the data (SP 800-185, §2.3, §3.3):

## 200 bytes, 25 lanes

The state is a 5 × 5 array of **lanes**, each `w = 64` bits (FIPS 202, §3.1, Table 1): 200 bytes,
exactly 25 registers on a 64-bit core. Because bit `z` of a lane is bit `z` of the string (§3.1.2)
and bits fill bytes from the low end (Appendix B.1), each lane is a **little-endian** 64-bit word.
A little-endian core loads it directly, unlike the big-endian words of [SHA-512](../sha512/).

Absorbing touches only the first `r/64` lanes: 17 for SHA3-256, 21 for SHAKE128 (§7, Table 3).
The other 8 or 4 lanes are the capacity. The state view in the labs above shows all 200 bytes in
this byte order.

<Lens level="engineer">

Each rate block costs one full permutation, so a larger capacity means a slower hash: SHA3-512
absorbs 72 bytes per permutation, SHA3-224 absorbs 144 (FIPS 202, §7, Table 3).

</Lens>

</LessonSection>

<LessonSection part="break">

## Mallory finds no handle

A [SHA-512](../sha512/) digest **is** the chaining value, so Mallory can keep hashing from it. A
SHA3-256 digest is only 256 rate bits; the 512-bit capacity never leaves the sponge (FIPS 202, §4,
§6.1), so there is no state to extend: SHA-3 resists length extension (Appendix A.1).

Drop the suffix bits and `SHA3-256(M)` and `SHAKE256(M)` become the same sponge, `KECCAK[512]`, on
the same input (§6.1–6.2). Keccak won the SHA-3 competition (2007–2012; NIST IR 7896); the
suffixes appeared in the May 2014 draft of FIPS 202 (§1). Ethereum specifies Keccak version 3,
"rather than the final SHA-3 specification" (Yellow Paper, §3), so its `Keccak-256("abc")` is
`4e03657a …`, not `3a985da7 …`.

<Lens level="cryptographer">

Bertoni, Daemen, Peeters and Van Assche (EUROCRYPT 2008) prove the sponge on a random permutation
indifferentiable from a random oracle up to about 2<sup>c/2</sup> queries: SHAKE128 (`c = 256`)
claims at most 128 bits at any output length (FIPS 202, Appendix A.1, Table 4).

</Lens>

## Check yourself

<CheckQuestion
  id="sha3-256-rate"
  number={1}
  question="How many message bytes does SHA3-256 absorb per Keccak-f[1600] permutation?"
  options={['64', '128', '136', '200']}
  answer={2}
>
  SHA3-256 has capacity `c = 512` (FIPS 202, §6.1), so the rate is `1600 − 512 = 1088` bits, 136
  bytes (§7, Table 3). The remaining 64 bytes of the 200-byte state are never XORed with input.
</CheckQuestion>

<CheckQuestion
  id="shake128-pad-byte"
  number={2}
  question="A byte-aligned message is hashed with SHAKE128. Which byte follows the message (when padding needs at least two bytes)?"
  options={['01', '06', '1f', '80']}
  answer={2}
>
  SHAKE128 appends the suffix `1111`, and pad10\*1 adds a `1` (FIPS 202, §6.2, §5.1). Filled from
  the least significant bit, `1111 1` is `0x1f`; the last pad byte is `0x80` (Appendix B.2). SHA3
  gives `06`, original Keccak `01`.
</CheckQuestion>

<CheckQuestion
  id="sponge-no-length-extension"
  number={3}
  question="Why can't a SHA3-256 digest be used to continue hashing the way a SHA-256 digest can?"
  options={[
    'SHA3-256 uses more rounds than SHA-256',

    'SHA3-256 pads with a 128-bit length field',

  answer={1}
>
  Continuing needs the full 1600-bit state. The digest reveals 256 rate bits; the 512-bit capacity
  never leaves the sponge (FIPS 202, §4, §6.1), so SHA-3 resists length extension (Appendix A.1).
</CheckQuestion>
