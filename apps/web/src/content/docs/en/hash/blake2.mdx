## Add, rotate, XOR

BLAKE2 uses three word operations: addition, rotation and XOR (**ARX**), with no S-box. It refines
BLAKE, a SHA-3 finalist (NIST IR 7896, §3). **BLAKE2s** works on 32-bit words, **BLAKE2b** on 64-bit
words (RFC 7693, §1, §2.1).

F copies the chaining value `h` and the IV into a 16-word work vector `v`, a 4 × 4 matrix. Each
round runs the mixing function **G** on the four columns, then the four diagonals (RFC 7693, §3.2).
Finally both halves of `v` are XORed into `h`.

## The first G of "abc"

The lab hashes RFC 7693's Appendix B example: BLAKE2s-256 of "abc". The message block holds
`m[0] = 00636261` (little-endian, §2.4) and zeros. `init` sets `h[0] = 6a09e667 ⊕ 01010020 = 6b08e647`.

## G, columns, diagonals

G mixes four words `a, b, c, d` with two message words `x, y` (RFC 7693, §3.1). The rotation
counts are R1…R4 = 16, 12, 8, 7 for BLAKE2s and 32, 24, 16, 63 for BLAKE2b (§2.1).

<Formula caption="Mixing function G, RFC 7693 §3.1 (+ is addition mod 2ʷ, ⋙ rotates right).">
{`a ← a + b + x     d ← (d ⊕ a) ⋙ R1
c ← c + d         b ← (b ⊕ c) ⋙ R2
a ← a + b + y     d ← (d ⊕ a) ⋙ R3
c ← c + d         b ← (b ⊕ c) ⋙ R4`}
</Formula>

<Formula caption="One round of F, RFC 7693 §3.2 (s = SIGMA[i mod 10], §2.7).">
{`columns:    G(v0, v4, v8,  v12)  G(v1, v5, v9,  v13)  G(v2, v6, v10, v14)  G(v3, v7, v11, v15)
diagonals:  G(v0, v5, v10, v15)  G(v1, v6, v11, v12)  G(v2, v7, v8,  v13)  G(v3, v4, v9,  v14)`}
</Formula>

The `i`-th G call takes `m[s[2i]]` and `m[s[2i+1]]`; SIGMA reorders the 16 message words each round
(§2.7). The core permutation is based on the one in Bernstein's ChaCha stream cipher (Aumasson et
al. 2013, §4.1). The round-detail lab shows BLAKE2b's 12 rounds one at a time:

is a byte shuffle on SSSE3 CPUs (Aumasson et al. 2013, §2.2).

## Little-endian, 168 bytes

BLAKE2 reads bytes into words **little-endian** (RFC 7693, §2.4), like MD5 and unlike SHA-2,
because most target CPUs are little-endian (Aumasson et al. 2013, §2.5); see
[endianness](../../foundations/endianness/). The digest is the first `nn` bytes of `h`, written
little-endian (§3.3).

A BLAKE2s implementation keeps the chaining value (32 bytes), the message block (64), the work vector
(64) and the counter (8) in RAM: **168 bytes**, against 232 for BLAKE-256 (Aumasson et al. 2013,
§3.3).

The four column calls of G touch disjoint words, and so do the four diagonal calls (§3.2), so
SIMD code can run them side by side, one G per vector lane.

<Lens level="engineer">

The state view groups `v` as four rows of four words, so a column G is one vertical line and a
diagonal G wraps around. Every word in it is shown in the byte order the RFC stores
(`byteOrder: little`).

</Lens>

## Counter, flag, key, rounds

**Parameter word 0.** `h[0] ⊕= 0x0101kknn` folds digest length `nn` and key length `kk` into the
start (RFC 7693, §2.5, §3.3). Without it, BLAKE2s-128 would be half of BLAKE2s-256.

**Counter and final flag.** `t` counts bytes so far; `f` inverts `v[14]` for the last block only
(§3.2). Zero padding suffices because `t` encodes the length (Aumasson et al. 2013, §4.2). No honest
computation feeds a *finalized* digest state into a non-final block, hence the designers' claimed
immunity to length extension (abstract), unlike SHA-256.

**Key.** The zero-padded key becomes block 0 (§3.3): a prefix MAC without HMAC (§1), at least one
compression cheaper (Aumasson et al. 2013, §2.9). WireGuard's `Mac` is keyed BLAKE2s; its KDF still
uses HMAC-BLAKE2s (Donenfeld, NDSS 2017, §5.4).

| 32-bit (BLAKE-256, BLAKE2s) | 14 | 10 | 6.75 rounds, 2²⁵³·⁸ | 7 |
| 64-bit (BLAKE-512, BLAKE2b) | 16 | 12 | 7.5 rounds, 2⁵¹⁰·³ (Espitau et al. 2015) | 8 |

<CheckQuestion
  id="blake2-final-flag-word"

>
  If the final block flag `f` is set, `v[14] ← v[14] ⊕ 0xFF..FF` (RFC 7693, §3.2). The counter `t`
  goes into `v[12]` and `v[13]`; there is no length field in the padding.
</CheckQuestion>
