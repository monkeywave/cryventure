## A fingerprint of fixed size

A **hash function** maps a message of almost any length to a fixed-size **digest**. It is
deterministic, public and has **no key**: anyone can recompute `H(m)` (FIPS 180-4, §1, Figure 1).

<KeyFacts>
  <KeyFact label="Message" value="< 2⁶⁴ bit" kind="plaintext" />
  <KeyFact label="Block" value="512 bit" kind="state" />
  <KeyFact label="SHA-256 digest" value="256 bit" kind="ciphertext" />
</KeyFacts>

SHA-2 is a **Merkle–Damgård** design (Merkle 1989; Damgård 1989): **pad** the message to whole
512-bit blocks (§5.1.1), then feed them one by one into a **compression function**. Its output, the
**chaining value** `H⁽ⁱ⁾`, enters the next block; step 4 of §6.2.2 adds the old one back in: the
**feed-forward**.

<Formula caption="Merkle–Damgård chaining in SHA-256, FIPS 180-4 §5.3.3 and §6.2.2 (+ is addition mod 2³² per word).">
{`H⁽⁰⁾ = IV
H⁽ⁱ⁾ = H⁽ⁱ⁻¹⁾ + compress(H⁽ⁱ⁻¹⁾, M⁽ⁱ⁾)    i = 1 … N
H(m) = H⁽ᴺ⁾`}
</Formula>

<WhyBox constant="64-bit length" title="why the padding ends with the length">
  The padding ends with the message length `ℓ` in 64 bits (FIPS 180-4 §5.1.1; 128 bits for
  SHA-384/512, §5.1.2). This "strengthening" makes every collision of the hash a collision of the
  compression function (Damgård 1989; HAC §9.4.1), and caps messages below 2⁶⁴ bits.
</WhyBox>

<Lens only="story">

A blender with memory: it mixes one 64-byte scoop at a time into what is already there.

</Lens>

</LessonSection>

## Two blocks, one chain

The lab hashes the two-block message of NIST's "Examples with Intermediate Values" (SHA256.pdf):
`abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq`, 56 bytes = 448 bits. The padding needs
at least 1 + 64 bits, which no longer fit into the first block, so the message becomes two 512-bit
blocks (FIPS 180-4, §5.1.1).

Watch the chaining value: after block 1, `H⁽¹⁾` is the starting state of block 2, and only `H⁽²⁾`
is the digest `248d6a61 … 19db06c1`.

## Padding "abc"

FIPS 180-4, §5.1.1 pads a message of `ℓ` bits like this: append one `1` bit, then `k` zero bits
with `ℓ + 1 + k ≡ 448 (mod 512)`, then `ℓ` as a 64-bit big-endian integer. Its own example is
"abc": `ℓ = 24`, so `k = 448 − 25 = 423`.

<Formula caption='The padded 512-bit block of "abc" (FIPS 180-4 §5.1.1), in hex.'>
{`61 62 63                 "abc" (24 bits)
80                       1 bit, then 7 zero bits
00 × 52                  416 more zero bits (423 in total)
00 00 00 00 00 00 00 18  ℓ = 24 = 0x18 as 64 bits`}
</Formula>

3 + 1 + 52 + 8 = 64 bytes: exactly one block. §5.2.1 then reads it as sixteen 32-bit words
`M₀ … M₁₅`, here `61626380`, `00000000`, …, `00000018`. One compression from the initial hash value
(§5.3.3) gives `ba7816bf … f20015ad`.

<Lens level="cryptographer">

Because the last block encodes `ℓ`, two colliding messages of different lengths differ in that
block, and equal lengths force a collision at some block along the chain. Either way the compression
function collides: Damgård's proof (1989; HAC §9.4.1).

</Lens>

</LessonSection>

## Eight words of state

The whole SHA-256 state between blocks is the chaining value: eight 32-bit words, 32 bytes
(FIPS 180-4, §6.2.2). Words are **big-endian** (§3.1), so a little-endian x86 or ARM core byte-swaps
each word it loads from the message block; the [endianness lesson](../foundations/endianness/)
shows why.

Modern CPUs have instructions for the compression function: Intel's SHA extensions (SHA-NI) and
the ARMv8 SHA2 instructions. The [SHA-256 page](./sha256/) runs them in its hardware lab.

</LessonSection>

## Mallory's three targets

A hash function should resist three attacks (SP 800-107 Rev. 1, §4.1):

| Notion | Mallory is given | and must find | Generic cost |
|---|---|---|---|
| Preimage | a digest `y` | any `m` with `H(m) = y` | about 2ⁿ |
| Second preimage | a message `m` | `m′ ≠ m` with `H(m′) = H(m)` | about 2ⁿ |
| Collision | nothing | any `m ≠ m′` with `H(m) = H(m′)` | about 2ⁿᐟ² |

Collisions are cheapest because of the **birthday bound**: among about 2ⁿᐟ² random digests, two
probably match (HAC §9.7.1). So SHA-256 offers **128-bit** collision strength and 256-bit
preimage strength (SP 800-107 Rev. 1, §4.2, Table 1; SP 800-57 Part 1 Rev. 5, Table 3).

History shows collisions fall first: MD5 (Wang & Yu, EUROCRYPT 2005) and SHA-1 ("SHAttered",
Stevens et al., CRYPTO 2017) both lost collision resistance through cryptanalysis.

<Lens level="cryptographer">

Rogaway and Shrimpton (FSE 2004) formalise these as Pre, Sec and Coll, and show how they relate.
Collision resistance needs care: for a fixed, unkeyed `H`, a collision always *exists*, so it is
defined as "no one can *find* one". Second preimages of 2ᵏ-block messages cost about 2ⁿ⁻ᵏ for
Merkle–Damgård (Kelsey & Schneier, EUROCRYPT 2005), hence SP 800-107's range of 201–256 bits.

</Lens>

  options={['64 bits', '128 bits', '192 bits', '256 bits']}

  By the birthday bound, a generic collision search costs about 2²⁵⁶ᐟ² = 2¹²⁸ hash evaluations
  (SP 800-107 Rev. 1, §4.2, Table 1).

<CheckQuestion
  id="hash-notion-collision"
  number={3}
  question="Mallory may choose both messages freely and wins if they have the same digest. Which property does she attack?"
  options={['Preimage resistance', 'Second-preimage resistance', 'Collision resistance', 'Confidentiality of the key']}
  answer={2}
>
  Choosing both messages is the collision game; in the second-preimage game the first message is
  given to her (SP 800-107 Rev. 1, §4.1). A hash function has no key.
