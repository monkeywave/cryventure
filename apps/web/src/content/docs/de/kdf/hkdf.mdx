## Ein Geheimnis rein, viele Schlüssel raus

Eine **Schlüsselableitungsfunktion** (KDF, engl. *key derivation function*) macht aus geheimem
Material, etwa einem gemeinsamen Diffie-Hellman-Geheimnis, die Schlüssel, die ein Protokoll
verwendet (RFC 5869, §1). HKDF hat zwei [HMAC](../../mac/hmac/)-basierte Hälften,
**Extract-then-Expand** (Krawczyk, CRYPTO 2010; RFC 5869, §1):

<KeyFacts>
  <KeyFact label="Extract" value="PRK = HMAC(Salt, IKM)" kind="key" />
  <KeyFact label="Expand" value="OKM, L Byte" kind="ciphertext" />
  <KeyFact label="Max. L" value="255 · HashLen" kind="constant" />
</KeyFacts>

**Extract** verdichtet ungleichmäßig zufälliges Eingabeschlüsselmaterial (IKM, engl. *input keying
material*) zu einem **pseudozufälligen Schlüssel** (PRK, §2.2). **Expand**
dehnt den PRK auf so viel Ausgabeschlüsselmaterial (OKM) wie nötig, gebunden an einen
Kontextstring `info` (§2.3).

<WhyBox constant="255 · HashLen" title="warum die Ausgabe begrenzt ist">
  Expand nummeriert seine Blöcke mit einem einzigen Zählerbyte, `0x01` … `0xff`, also gibt es
  höchstens 255 Blöcke zu je HashLen Byte: 8160 Byte für SHA-256 (RFC 5869, §2.3).
</WhyBox>

<Lens only="story">

gestempelt.

## Erst Extract, dann Expand

<Formula caption="HKDF, RFC 5869, §2.2 und §2.3 (‖ = Verkettung, N = ⌈L / HashLen⌉).">
{`PRK  = HMAC-Hash(salt, IKM)
T(0) = leerer String
T(i) = HMAC-Hash(PRK, T(i−1) ‖ info ‖ i)      i = 0x01 … N
OKM  = die ersten L Byte von T(1) ‖ T(2) ‖ … ‖ T(N)`}
</Formula>

Das **Salt** ist optional: Ist es leer, nimmt Extract HashLen Nullbyte (§2.2). Ein zufälliges Salt
„adds significantly to the strength of HKDF“ und muss nicht geheim sein (§3.1). **Info** bindet
jeden Schlüssel an seinen Zweck: Verschiedene Info, unabhängige Schlüssel aus demselben PRK (§3.2).

## Zwischenzustände und kurzlebige Geheimnisse

Der PRK ist der HMAC-Schlüssel jedes Expand-Blocks. Der innere und der äußere Hash von HMAC
absorbieren zuerst `K0 ⊕ ipad` bzw. `K0 ⊕ opad`, also kann eine Implementierung diese beiden
Zwischenzustände (Midstates) einmal pro Schlüssel speichern (RFC 2104, §4). In Testfall A.1 ist
jede Eingabe für `T(i)` höchstens 32 + 10 + 1 = 43 Byte lang, also kostet danach jeder Block zwei
SHA-256-Kompressionen.

| Wert | Größe (A.1) | Geheim? |
|---|---|---|
| IKM | 22 Byte | ja |
| Salt, Info | 13 bzw. 10 Byte | nein (RFC 5869, §3.1, §3.2) |
| PRK | HashLen = 32 Byte | ja |
| OKM | L = 42 Byte | ja |

RFC 8446 (§7.1) empfiehlt (SHOULD), ein Secret zu löschen, sobald alle daraus abgeleiteten Werte berechnet
sind. Wie lange solche Schlüssel im Speicher eines Prozesses liegen bleiben, ist Thema einer
späteren Phase.

</LessonSection>

## Mallorys Abkürzungen

**Extract überspringen.** RFC 5869 erlaubt das nur, wenn das IKM bereits ein gleichverteilt
zufälliger Schlüssel ist; ein Diffie-Hellman-Wert ist das nicht, erst Extract macht einen daraus
(§3.3).

**Info weglassen.** Zwei Schlüssel aus demselben PRK mit gleicher Info und gleichem L sind
identisch. Kommen ein Verschlüsselungsschlüssel und ein MAC-Schlüssel gleich heraus, sind die beiden
Verwendungen nicht mehr unabhängig; verschiedene Info-Strings halten sie auseinander (§3.2).

**Ein Passwort einspeisen.** Extract „can concentrate existing entropy but cannot amplify entropy“,
und HKDF hat keinen Mechanismus, der einen Wörterbuchangriff bremst (§4). Jeder Passwortversuch von
Mallory kostet nur ein paar HMAC-Aufrufe. Passwörter brauchen eine absichtlich langsame KDF wie
[PBKDF2](../pbkdf2/) (RFC 5869, §4 verweist auf PKCS #5).

<Lens level="engineer">

Wer L > 255 · HashLen anfordert, bekommt einen Fehler, keinen längeren Schlüssel (RFC 5869, §2.3).

</Lens>

<CheckQuestion
  id="hkdf-max-length"
  number={2}
  question="Wie lang kann das OKM von HKDF-SHA-256 höchstens sein?"
  options={['32 Byte', '255 Byte', '8160 Byte', 'Unbegrenzt']}
  answer={2}
>
  L ≤ 255 · HashLen (RFC 5869, §2.3), weil der Blockzähler ein Byte hat: 255 · 32 = 8160 Byte.
</CheckQuestion>

<CheckQuestion
  id="hkdf-not-for-passwords"
  number={3}
  question="Warum ist HKDF die falsche Wahl, um einen Schlüssel aus einem Passwort abzuleiten?"
  options={[

  answer={2}
>
  Extract verdichtet nur die vorhandene Entropie, und HKDF hat keinen Arbeitsfaktor gegen
