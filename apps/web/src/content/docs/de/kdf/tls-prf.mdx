## Ein Secret hinein, beliebig viele Bytes heraus

Ein Handshake von TLS 1.0–1.2 endet mit einem **Pre-Master Secret**. Die PRF macht daraus das
48 Byte lange **Master Secret**, gebunden an die Zufallswerte beider Hello-Nachrichten, und aus dem
Master Secret den **Schlüsselblock** (engl. *key block*) mit den MAC-Schlüsseln, den
Verschlüsselungsschlüsseln und den IVs der Sitzung (RFC 5246 §8.1, §6.3; RFC 2246 §8.1, §6.3).

Die PRF nimmt ein Secret, ein ASCII-**Label** und einen **Seed** und erweitert sie mit
[HMAC](../../mac/hmac/) auf so viele Bytes wie verlangt (RFC 5246 §5). Das Label benennt den
Zweck: „master secret“ (§8.1) oder „key expansion“ (§6.3), die beiden Ausgaben entstehen also aus
verschiedenen Eingaben.

  <KeyFact label="TLS 1.0/1.1" value="P_MD5 ⊕ P_SHA-1" kind="constant" />
  <KeyFact label="TLS 1.2" value="P_SHA256" kind="constant" />

<WhyBox constant="48" title="warum das Master Secret 48 Byte hat">
  RFC 5246 §8.1 legt es fest:
  `PRF(pre_master_secret, "master secret", ClientHello.random + ServerHello.random)[0..47]`,
  „always exactly 48 bytes“, egal, was der Schlüsselaustausch geliefert hat.
</WhyBox>

<Lens only="story">

Ein Rezept, das ein gemeinsames Geheimnis zu so vielen frischen Schlüsseln verrührt, wie das
Gespräch braucht.

</Lens>

## Die A(i)-Kette

<Formula caption="P_hash, RFC 5246 §5 (+ = Verkettung). TLS 1.2: PRF = P_SHA256(secret, label + seed).">
{`A(0) = label + seed
A(i) = HMAC_hash(secret, A(i−1))
P_hash(secret, label + seed) = HMAC_hash(secret, A(1) + label + seed) +
                               HMAC_hash(secret, A(2) + label + seed) + …`}
</Formula>

Die Kette `A(i)` speist nur die Blöcke; jeder Ausgabeblock hasht zusätzlich erneut den Seed.
P_hash läuft so oft wie nötig und verwirft den Überschuss (RFC 5246 §5).

<Formula caption="PRF von TLS 1.0/1.1, RFC 2246 §5 (unverändert in RFC 4346 §5).">
{`S1 = erste ⌈|secret| / 2⌉ Byte       S2 = letzte ⌈|secret| / 2⌉ Byte
PRF(secret, label, seed) = P_MD5(S1, label + seed) ⊕ P_SHA-1(S2, label + seed)`}
</Formula>

Bei ungerader Länge ist das letzte Byte von S1 das erste von S2 (RFC 2246 §5). TLS 1.2 verzichtet
auf die Teilung und nutzt einen einzigen Hash: SHA-256 für seine eigenen Suites, und jede Suite
muss ihre PRF nennen (RFC 5246 §5); die `*_SHA384`-Suites aus RFC 5289 nutzen `P_SHA384`
(RFC 5289 §3).

<Lens level="cryptographer">

RFC 2246 §5 nennt das XOR eine Absicherung: Es „should guarantee its security if either algorithm
remains secure“. Allerdings bekommt jede Hälfte nur die Hälfte des Secrets als Schlüssel.

</Lens>

</LessonSection>

## Was im Speicher liegt

Während der PRF hält ein TLS-Stack das Secret als HMAC-Schlüssel, das aktuelle `A(i)`, Label und
Seed sowie einen Ausgabepuffer. Dank HMAC kann er den aufgefüllten Schlüssel einmal hashen und den
inneren und den äußeren Zustand mit Schlüssel für jeden weiteren Aufruf behalten (RFC 2104 §4); so
kostet jedes `A(i)` und jeder Block zwei Kompressionen einer kurzen Nachricht.

Was den Handshake überlebt, ist das 48 Byte lange Master Secret: TLS 1.2 bewahrt es mit der
Sitzung auf, damit eine Sitzungswiederaufnahme neue Schlüssel daraus ableiten kann (RFC 5246 §8.1,
§7.3). Wer diese 48 Byte und die öffentlichen Zufallswerte liest, kann die PRF mit dem Label
„key expansion“ erneut ausführen und die Sitzung entschlüsseln.

<Lens level="engineer">

Der Schlüsselblock nutzt `server_random + client_random`, das Master Secret `client_random +
server_random` (RFC 5246 §6.3, §8.1). Vertauschst du sie, bekommst du plausibel aussehende, aber
falsche Schlüssel.

</Lens>

</LessonSection>

## Geschichte: der Triple Handshake

Das Master Secret von TLS 1.2 hängt nur vom Pre-Master Secret und den beiden Zufallswerten ab
(RFC 5246 §8.1). Bhargavan et al. (IEEE S&P 2014) zeigten, dass ein bösartiger Server zwei
verschiedene Verbindungen, eine mit dem Client und eine mit einem echten Server, mit **demselben**
Master Secret enden lassen kann. Zusammen mit Sitzungswiederaufnahme und Neuaushandlung
(engl. *renegotiation*) brach das die Client-Authentifizierung, auf die sich Anwendungen verließen
(RFC 7627 §1). Diese Seite erzählt die Geschichte, nicht die Angriffsschritte.

Die Lösung, RFC 7627, bindet das Master Secret an den ganzen Handshake:

<Formula caption="RFC 7627 §4; session_hash ist der Hash der bisherigen Handshake-Nachrichten (§3).">
{`master_secret = PRF(pre_master_secret, "extended master secret", session_hash)[0..47]`}
</Formula>

TLS 1.3 hat die PRF durch [HKDF](../hkdf/) ersetzt und hasht das Transkript in seinen gesamten
Key Schedule (RFC 8446 §1.2, §7.1).

<Lens level="cryptographer">

P_hash selbst hat hier nichts falsch gemacht: Es war eine solide PRF, die einen Seed bekam, der zu
wenig vom Handshake abdeckte. RFC 7627 korrigiert die Eingabe, nicht die Funktion (RFC 7627 §1,
§4).

</Lens>

</LessonSection>

## Teste dich selbst

<CheckQuestion
  id="p-hash-a-chain"
  number={1}
  question="Was ist A(2) in P_hash?"
  options={[
    'HMAC(secret, A(1) + seed)',
    'HMAC(secret, A(1))',
    'HMAC(A(1), secret)',
    'A(1) ⊕ seed',
  ]}
  answer={1}
>
  RFC 5246 §5: `A(i) = HMAC_hash(secret, A(i−1))`, wobei `A(0)` Label plus Seed ist. Die
  Ausgabeblöcke sind `HMAC_hash(secret, A(i) + seed)`; die Kette selbst sieht den Seed nie wieder.
</CheckQuestion>

<CheckQuestion
  id="tls10-prf-hedge"
  number={2}
  question="Warum verknüpft die PRF von TLS 1.0 eine P_MD5- und eine P_SHA-1-Ausgabe per XOR?"
  options={[
    'Damit die PRF doppelt so schnell wird',
    'Damit sie sicher bleibt, solange einer der beiden Hashes sicher bleibt',
    'Weil MD5 allein zu wenige Bytes liefert',
    'Um das Master Secret zu verschlüsseln',
  ]}
  answer={1}
>
  RFC 2246 §5 nutzt zwei Hash-Algorithmen „in a way which should guarantee its security if either
  algorithm remains secure“. TLS 1.2 gab diese Absicherung zugunsten eines einzigen, stärkeren
  Hashs auf (RFC 5246 §5).
</CheckQuestion>

<CheckQuestion
  id="extended-master-secret-seed"
  number={3}
  question="Was nutzt das Extended Master Secret aus RFC 7627 als Seed?"
  options={[
    'ClientHello.random + ServerHello.random',
    'ServerHello.random + ClientHello.random',
    'Einen Hash der Handshake-Nachrichten (den Session-Hash)',
    'Das Master Secret der vorherigen Sitzung',
  ]}
  answer={2}
>
  RFC 7627 §4 leitet das Master Secret aus `session_hash` ab, dem Hash des Handshake-Transkripts
  (§3); so können zwei verschiedene Handshakes nicht wie beim Triple Handshake mit demselben Master
  Secret enden (Bhargavan et al., IEEE S&P 2014).
</CheckQuestion>
