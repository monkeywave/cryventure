## Eine Blockchiffre allein verschlüsselt noch keine Nachrichten

AES verschlüsselt genau einen 16-Byte-Block. Echte Nachrichten sind länger, also brauchen wir einen
**Betriebsmodus**: eine Vorschrift, wie die Blockchiffre auf viele Blöcke angewendet wird. NIST
SP 800-38A definiert fünf davon. Der einfachste ist **Electronic Codebook**, kurz ECB (§6.1) – das
elektronische Codebuch.

ECB zerlegt die Nachricht in Blöcke `P₁ … Pₙ` und verschlüsselt jeden davon für sich, immer mit
demselben Schlüssel. Kein Block beeinflusst einen anderen.

<Formula caption="ECB-Verschlüsselung und -Entschlüsselung, NIST SP 800-38A §6.1.">
{`Cⱼ = E_K(Pⱼ)        für j = 1 … n
Pⱼ = D_K(Cⱼ)        für j = 1 … n`}
</Formula>

<Lens only="story">

Stell dir ein riesiges Codebuch vor, mit einer Seite pro Schlüssel: Jeder mögliche 16-Byte-Block hat
darin genau ein festes Codewort. Verschlüsseln heißt, jeden Block im Buch nachzuschlagen. Wer
dasselbe Codewort zweimal sieht, weiß, dass zweimal derselbe Block gesendet wurde.

</Lens>

</LessonSection>

## Block für Block, ohne Gedächtnis

1. **Auffüllen:** Fülle den Klartext per Padding auf volle Blöcke auf (siehe Teil 4).
2. **Zerlegen:** Teile ihn in 16-Byte-Blöcke `P₁ … Pₙ`.
3. **Verschlüsseln:** Verschlüssle jeden Block mit der Blockchiffre: `Cⱼ = E_K(Pⱼ)`. Die Reihenfolge
   spielt keine Rolle, daher können alle Blöcke parallel verarbeitet werden – beim Ver- wie beim
   Entschlüsseln (SP 800-38A §6.1).

ECB kennt weder IV noch Zähler. Das Verfahren ist **deterministisch**: Unter demselben Schlüssel wird
ein bestimmter Klartextblock immer zum selben Geheimtextblock. SP 800-38A §6.1 sagt es selbst: Ist
das unerwünscht, verwende kein ECB.

Im Lab werden beide Blöcke `41545441434b204154204441574e2121` zu
`541ff0c92b9251ae06c624c4a8ab2a85` verschlüsselt.

<Lens level="cryptographer">

Jedes deterministische Verfahren scheitert an IND-CPA: Der Angreifer lässt sich vom
Verschlüsselungsorakel `E(m₀)` geben, reicht dann `m₀, m₁` als Challenge ein und vergleicht. ECB
scheitert sogar innerhalb einer einzigen Nachricht, weil sich gleiche Blöcke wiederholen. Außerdem
kann ein Angreifer ganze Geheimtextblöcke **umsortieren, weglassen oder neu zusammensetzen**, ohne
dass beim Entschlüsseln ein Fehler auftritt.

</Lens>

</LessonSection>

## So sieht ECB-Geheimtext aus

Der Geheimtext ist einfach `C₁ ‖ C₂ ‖ … ‖ Cₙ`: Block `j` beginnt bei Byte `16·(j − 1)`, ohne
Header, IV oder Tag.

ECB braucht ganze Blöcke. SP 800-38A überlässt das Padding der Anwendung (Anhang A); verbreitet ist
**PKCS#7** (RFC 5652, §6.3): Häng `k − (len mod k)` Byte an, jedes mit genau diesem Wert, wobei `k`
die Blockgröße ist. Es kommen also immer zwischen 1 und 16 Byte hinzu.

<WhyBox constant="0x10" title="ein voller Block Padding">
  Unsere 32-Byte-Nachricht füllt bereits genau zwei Blöcke, trotzdem hängt RFC 5652 §6.3 noch 16 Byte
  `10` (= 16) an. Das Padding ist nie leer, deshalb kann der Empfänger immer das letzte Byte lesen und
  genau so viele Bytes entfernen. Das ist der dritte Block `a254be88…` im Lab.
</WhyBox>

Ein Bitfehler in `Cⱼ` verfälscht nur `Pⱼ`; alle anderen Blöcke werden korrekt entschlüsselt
(SP 800-38A, Anhang D).

</LessonSection>

## Mallory sieht sich den Pinguin an

Ein Bild ist eine lange Folge von Pixelbytes. Einfarbige Flächen erzeugen viele identische
16-Byte-Blöcke, und ECB macht daraus identische Geheimtextblöcke. Die Farben werden zu Rauschen,
aber die **Kanten** zwischen den Flächen bleiben, wo sie sind: Der Umriss übersteht die
Verschlüsselung.

Das ist der klassische „ECB-Pinguin“, ein Bild, das seit zwei Jahrzehnten in der
Kryptografielehre kursiert. Unser Pinguin ist eine eigene Zeichnung und wird live in deinem Browser
mit AES verschlüsselt. Schalte auf CBC um (nächste Lektion), und das Bild wird zu gleichmäßigem
Rauschen.

aber jeder wiederholte Block ist sichtbar. Verwende ECB nie für mehr als einen einzelnen Block aus
Zufallsdaten.
