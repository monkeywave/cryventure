# M4 — GCM + Memory & Hardware: design brief

This is the shared contract for everyone working on M4. The decisions here are binding; record any
deviation in `docs/STATUS.md`. The format follows `docs/M3.md`.

M4 has two halves:

- **GCM:** GHASH and GCM producers over the `BlockCipher` port, with their lessons.
- **Memory & Hardware (the extensibility proof, PLAN §7):** derivers `isa-x86`, `isa-armv8` and
  `memory`, and views `instructions`, `registers` and `memory`. They arrive **as plugins only**.

## 0. Core-diff budget ("no core diff" proof)

Core may change in exactly two ways in M4, and both land in **wave 1**, before any deriver or view
exists:

1. **Facet schemas** (§3): new files `facets/{align,instructions,registers,memory,field}.ts`, plus
   additive union members in `facets/chain.ts` and `facets/wire.ts`.
2. **GCM reference math** (§2), following the M3 §3 precedent (`core/modes/*` and `core/math/gf256`
   are the untraced references that the traced producers and the oracles share):
   - `core/math/gf128.ts`
   - `core/modes/gcm.ts`
   - an optional `increment` argument on `ctrXor` plus an exported `inc32`, so GCM **reuses**
     `core/modes/ctr` instead of copying it.

   Without this, `ghash` and `gcm` would duplicate GF(2¹²⁸) code, because plugins never import
   each other.

**The proof:** wave 1 is committed on its own (`wip(m4): core facet schemas + GCM reference`). From
that commit on, `git diff <wave-1 commit> -- packages/core` must stay **empty** through derivers,
views, lessons and the reviews. The final review checklist checks this. `DeriverManifest`,
`viewsFor`, `ViewManifest`, `PrimitiveManifest`, `PortMap` and the tracer do **not** change.

Everything else is plugin, viz, tools or app code:

- the lazy deriver runtime lives in viz;
- the deriver-aware view list lives in apps/web;
- the deriver contract lives in tools;
- layouts and listings are data inside the deriver plugins.

## 1. Deriver contract in practice

The existing core contract is used as is:

```ts
interface DeriverManifest {
  kind: 'deriver'; id; apiVersion: 1;
  from: FacetKind[];
  provides: FacetKind[];
  appliesTo?(bundle): boolean;
  load(): Promise<DeriverModule>;
}
interface DeriverModule {
  derive(bundle: TraceBundle): Partial<Record<FacetKey, unknown>>;
}
```

### 1a. Package and discovery

- `packages/derivers/` is the new workspace package `@cryventure/derivers`, depending on
  `@cryventure/core` only. ESLint already declares `derivers` (`ALLOWED_WORKSPACE_DEPS.derivers =
  ['core']`).
- `src/index.ts` globs `./*/manifest.ts` (eager), keeps `kind === 'deriver'`, sorts by id and
  exports `deriverManifests`. `src/messages.ts` exports `loadDeriverMessages(lang)`, which is
  server-side only like the other message exports.
- **Plugin folders:** `isa-x86/`, `isa-armv8/` and `memory/`. Each has `manifest.ts`, `module.ts`,
  `i18n/{en,de}.json` and tests.
- **Namespace convention:** `deriver.<id>.*`. It is checked by the contract kit, not by a manifest
  field, because the manifest does not change.
- **Shared code:** `packages/derivers/src/_lib/` holds code the derivers share, such as finding the
  AES op steps in a state facet. It has no manifest, so the glob skips it. Add an ESLint element
  `plugin-lib` (`packages/*/src/_lib/**`): plugins of the same package may import it, and it may
  import core only. The same element is available to `packages/primitives/src/_lib` but is not
  needed there in M4.
- Derivers must be deterministic. Extend the ESLint ban on `Math.random`/`Date.now` to `derivers`.

### 1b. Applicability

- `from` lists the facet kinds a deriver reads. `appliesTo(bundle)` decides on the real bundle.
- **ISA and memory derivers:**
  - They apply to bundles with `producer.id === 'aes'` and **op detail**: the state facet has no
    `op: 'round'` steps.
  - They read the AES producer's **published facet contract**, never its code:
    - regions `state`, `w`, `roundKey`;
    - ops `input`, `keyExpansion`, `addRoundKey`, `subBytes`, `shiftRows`, `mixColumns` and `output`,
      with `round`;
    - the `values` facet's `subkey` entries.
  - A deriver that finds the contract broken throws. The contract kit runs the derivers over every
    preset of every primitive, so a renamed region fails CI.
- AES traces only encryption (`module.ts` `run`), so decryption instructions (AESDEC/AESIMC)
  are out of scope.

### 1c. Lazy derivation and memoisation (viz)

- `LabRoot` gets an optional prop `derivers: readonly DeriverManifest[]` (default `[]`), exposed
  through the lab context.
- `useFacet(kind, variant?)`:
  1. A facet in the bundle or the derived cache is `ready`.
  2. Otherwise, if some deriver `provides` the kind, `from` ⊆ the bundle's kinds and
     `appliesTo?.(bundle) ?? true` holds, the facet is `loading`, and derivation is requested.
  3. Otherwise the facet is `missing`.
- The variant argument is optional. Without one, `useFacet` returns `default` if it exists, else
  the **first** variant in insertion order. New hook `useFacetVariants(kind): string[]` lists the
  variants of the bundle plus the derived cache, after derivation.
- **Memoisation per bundle:** `deriveOnce(bundle, deriver)` in `viz/src/lab/derive.ts` caches in a
  `WeakMap<TraceBundle, Map<deriverId, Promise<facets>>>`. One `derive()` call returns **all** of a
  deriver's variants.
  - The result goes into the store with one `setDerivedFacets(bundle, facets)` (new, batch). It is
    ignored when the store's bundle has changed meanwhile (stale guard).
  - A re-run resets the cache (`withBundle` already clears `derivedFacets`).
- **Failure:** a deriver that throws or fails to load leaves its facets `missing`. It logs once
  with `console.error` and does not retry for that bundle.
- Derivers run on the main thread. They read facets and compute no crypto, so they are cheap.

### 1d. Deriver-aware view list (apps/web)

- `apps/web/src/labs/registry.ts` gets two functions:
  - `viewsForProducer(producer)`: `viewsFor(views, producer.facets, derivers)`. It is used before
    the first run (SSR poster, preloading).
  - `viewsForBundle(bundle)`: `viewsFor(views, availableFacetKinds(bundle), applicable)`, where
    `applicable` is the derivers with `from` ⊆ the kinds and `appliesTo(bundle)`. The session
    recomputes the view list after every run and re-run.

  Core's `viewsFor` stays unchanged.
- An explicit `layout` that names a view whose facets are unavailable for the bundle drops that
  panel. It does not crash.
- `Lab.astro` adds `loadDeriverMessages` for every deriver whose `from` ⊆ `producer.facets`.

### 1e. Time model: own timelines, `align` to state steps

- The **player stays on the producer's state timeline**. The facet-agnostic timeline is deferred
  again (STATUS backlog).
- A derived facet has **its own steps** (instructions, register writes, memory writes). Each step
  carries `align: { first, last }`, the **inclusive** range of state steps it covers. Here is
  AES-128 on x86 and on ARMv8:

  | Instruction | Covers |
  |---|---|
  | `aesenc` (round r) | SubBytes r, ShiftRows r, MixColumns r, AddRoundKey r |
  | `aese` (round r) | AddRoundKey r−1, SubBytes r, ShiftRows r |
  | `aesmc` | MixColumns r |

- **Semantics at playhead p:**
  - Step i is *current* iff `first ≤ p ≤ last`.
  - Its effects are *visible* iff `p ≥ last`.
  - An instruction in flight therefore shows the registers from **before** it. This is the
    teaching point: hardware has no visible SubBytes-only state.
- Instructions that do no AES math (loads, `ret`) get the zero-width span of the step before them,
  or `{ -1, -1 }` at the start.
- Spans are monotonic: `first` and `last` never decrease, and both lie in `[-1, stepCount − 1]`.
  The contract kit checks this (`alignIssues`, §3a).

### 1f. Facet variants

| Facet | Variants |
|---|---|
| `instructions`, `registers` | `x86_64-aesni`, `aarch64-armv8-ce` |
| `memory` | `<triple>+<impl>`: `x86_64-linux-gnu+c-ref`, `x86_64-linux-gnu+aesni`, `aarch64-linux-gnu+c-ref`, `aarch64-linux-gnu+armv8` |

- Every facet carries its own `label: I18nRef` and its metadata (`target`, `impl`). Views build
  their pickers from the data, not from the variant string.
- Views keep the chosen variant in component state.
- Deep-linking a variant is deferred.

## 2. GCM

### 2a. Core reference (wave 1)

- **`core/math/gf128.ts`** works on 16-byte blocks in GCM bit order (SP 800-38D §6.3: bit 0 is the
  MSB of byte 0, the coefficient of x⁰). It provides:
  - `gf128Mul(x, y)`: Algorithm 1, the right-shift algorithm with `R = 11100001 ‖ 0¹²⁰`;
  - `gf128MulSteps(x, y)`: the 128 iterations as explainers `{ bit, xBit, z, v, reduced }`, like
    `gf256Steps`;
  - `rightShift1`.
- **`core/modes/gcm.ts`** provides:
  - `ghash(h, blocks)` (§6.4, Y₀ = 0, block-aligned input, throws otherwise)
  - `gcmJ0(cipher, key, h, iv)`, which implements the J0 rule:
    - 96-bit IV: `IV ‖ 0³¹ ‖ 1`;
    - otherwise: `GHASH_H(IV ‖ 0^(s+64) ‖ [len(IV)]₆₄)`.
  - `gcmEncrypt(cipher, key, iv, aad, plaintext, tagBytes) → { ciphertext, tag }`
  - `gcmDecrypt(...) → { ok: true, plaintext } | { ok: false }`. On FAIL it releases no
    plaintext (§7.2).
  - `gcmAccepts(cipher)`: true iff `blockSize === 16` (PLAN §2b `accepts`).
  - `GCM_TAG_BYTES = [16, 15, 14, 13, 12, 8, 4]` (§5.2.1.2). 8 and 4 are allowed only with the
    Appendix C limits, which the lesson explains.
- **`core/modes/ctr.ts`:**
  - `inc32(block)`: the low 32 bits + 1 mod 2³², with the rest unchanged (§6.2).
  - `ctrXor(cipher, key, counterBlock, data, increment = incrementCounter)`.

  GCTR is `ctrXor(…, inc32)`. The existing CTR behaviour and tests are unchanged.
- **Tests:**
  - McGrew–Viega test cases 1–18, ghash and the mul against Algorithm 1 written independently
    in the test;
  - an inc32 wrap test (`…ffffffff` → `…00000000`, upper 96 bits unchanged);
  - a non-96-bit J0 case (TC 6).

### 2b. Producers

**`ghash`**

- **Params:**
  - `hHex` (16 B)
  - `inputHex` (16–64 B, a multiple of 16)
  - `detail: 'block' | 'bit'`
- **Steps:**
  - `block`: one step per block, `xorBlock` then `multiply`.
  - `bit`: each multiply expands into its 128 Algorithm 1 iterations (`mulBit`), at most 4 × 128
    steps.
- **Facets:** `state` (regions `h`, `block`, `x` (the accumulator), `z`/`v` at `bit` detail),
  `values`, `narration`, `field`.
- **Output:** `{ ghash }`.
- **Presets:**
  - McGrew–Viega TC 2's GHASH. H = `66e94bd4ef8a2c3b884cfa59ca342b2e`; the input is TC 2's C ‖
    len block. Recompute and check it in a test.
  - a one-block `bit`-detail preset.

**`gcm`** (port param `cipher`, like the M3 modes)

| Param | Notes |
|---|---|
| `cipher` | port `BlockCipher`; a run error unless `blockSize === 16` (`plugin.gcm.error.blockSize`) |
| `keyHex` | key sizes from the resolved cipher |
| `ivHex` | 1–64 B; 12 B is the fast path, anything else goes through the J0 GHASH |
| `aadHex` | 0–64 B (may be empty) |
| `inputHex` | 0–64 B (empty = **GMAC**) |
| `direction` | `encrypt` \| `decrypt` |
| `tagHex` | decrypt only, length = `tagBytes` |
| `tagBytes` | select from `GCM_TAG_BYTES`, default 16 |

- **Validation of empty hex params:** they need 0-length hex. Check `parseHexOfLength` with
  `[0, …]`. If core cannot express it, read the param locally in the plugin. That is not a core
  change.
- **Ops**, in order. Scope levels: phase → op. The phases are `setup`, `ctr`, `ghash` and `tag`.

  | Op | Phase | Does |
  |---|---|---|
  | `hashKey` | setup | H = E_K(0¹²⁸) |
  | `j0` | setup | either path |
  | `inc32` | ctr | per block |
  | `encryptCounter` | ctr | per block, opaque E_K |
  | `xorKeystream` | ctr | per block |
  | `ghashBlock` | ghash | per AAD/C/length block, as xor + multiply |
  | `lengthBlock` | ghash | |
  | `encryptJ0` | tag | |
  | `tag` | tag | MSB_t |
  | `verify` | tag | decrypt only: equal → output, else FAIL narrated, no plaintext |

- **Facets:**
  - `state`, `values` (role `tag` exists), `narration`;
  - `chain` with `mode: 'gcm'`: CTR lanes per block plus a GHASH lane (§3e kinds);
  - `wire`: nonce/IV, AAD, ciphertext, tag;
  - `field`: one step per GHASH multiply, with terms X⊕B, H and the product.
- **Outputs:**
  - encrypt: `{ ciphertext, tag }` (`ciphertext` may be empty for GMAC);
  - decrypt: `{ plaintext }` when authentic, else `{}`.
- **Zoom:** the cipher nodes carry `zoom`, as in M3 (encryptions of counter blocks, H and J0).
- **Presets:**
  - McGrew–Viega TC 2, TC 4 (AAD) and TC 6 (60-byte IV, J0 via GHASH);
  - GMAC (TC 4 key, AAD only);
  - a truncated 96-bit tag;
  - a decrypt preset with a valid tag;
  - a decrypt preset with a flipped tag bit (FAIL).

### 2c. Conformance and oracles

- `gcm/vectors/conformance.json`: McGrew–Viega "The Galois/Counter Mode of Operation (GCM)"
  (revised 2005) test cases 1–18, all within the 64-byte limits. `ghash/vectors/conformance.json`
  gets the GHASH values of TC 2 and TC 4.
- `gcm/vectors/wycheproof-aes-gcm.json`: a filtered copy of Wycheproof
  `testvectors_v1/aes_gcm_test.json` (Apache-2.0). It keeps the cases whose key size is 16/24/32,
  IV is 1–64 B, msg and aad are ≤ 64 B, and tag size is in `GCM_TAG_BYTES`. Record the source
  commit, the filter and the counts in the file.
  - A plugin test runs every case. `valid` and `acceptable` cases must reproduce ct and tag.
    `invalid` cases must give decrypt `{}`.
  - The cases with flag `SmallIv` / `LongIv` / `CounterWrap` exercise J0 and inc32.
- **Oracles** (`tools/src/oracles/gcm.oracle.test.ts`): fast-check against `@noble/ciphers` `gcm`
  (random keys, AAD, input 0–64 B, IV lengths noble accepts) and noble's `ghash`.

### 2d. Attack labs: not planned

The user decided on 2026-10-03 that attack labs need their explicit go-ahead. The GCM
nonce-reuse lab from PLAN is **not** planned. The GCM lesson covers the topic conceptually and
historically:

- the uniqueness requirement (SP 800-38D §8) and the 2³² invocation limit for random 96-bit IVs
  (§8.3);
- that a repeated nonce reveals the XOR of plaintexts and endangers authenticity. These are
  conceptual statements, with no recovery procedure;
- the history, by name: Joux's "forbidden attack" comment to NIST (2006), and Böck et al.,
  "Nonce-Disrespecting Adversaries" (USENIX WOOT 2016), which found repeated nonces on real
  HTTPS servers;
- AES-GCM-SIV (RFC 8452) as the misuse-resistant alternative.

Truncated tags are covered as forgery odds of about 2⁻ᵗ per attempt, with Appendix C's limits.
There is no lab.

## 3. Facet schemas (wave 1)

All schemas are `schemaVersion: 1`, JSON-serializable, with a `validate<Kind>Facet(facet): string[]`
next to each, as for chain and wire. Addresses are lowercase hex strings (`'0x7ffc…'`), so
64-bit values never pass through `number`.

### 3a. `facets/align.ts`

```ts
interface AlignSpan { first: number; last: number }   // inclusive state steps, −1 = initial
function alignIssues(spans: AlignSpan[], stepCount: number): string[]; // monotonic, in range, first ≤ last
function currentAt(spans, p): number | undefined;        // index i with first ≤ p ≤ last (last match)
function appliedThrough(spans, p): number;               // last index with last ≤ p, −1 if none
```

### 3b. `instructions`

```ts
type OperandRef =
  | { kind: 'reg'; name: string; valueRef?: string }
  | { kind: 'mem'; base: string; offset: number; size: number; valueRef?: string };
interface Instruction {
  address: string;            // offset in the listing, hex
  mnemonic: string; operands: string[];   // as printed (data, not prose)
  reads: OperandRef[]; writes: OperandRef[];
  align: AlignSpan;
  covers?: I18nRef[];         // the AES ops this instruction performs, in its order
  note?: I18nRef;             // e.g. the fusion note on aese/aesmc pairs
}
interface InstructionsFacet {
  kind: 'instructions'; schemaVersion: 1;
  isa: string;                // open: 'x86_64', 'aarch64', later 'riscv64'
  extension: string;          // 'aesni', 'armv8-ce'
  label: I18nRef;
  syntax: 'intel' | 'att' | 'arm';
  source: { compiler: string; flags: string; triple: string; function: string; compilerExplorerUrl?: string };
  instructions: Instruction[];
}
```

### 3c. `registers`

```ts
interface RegisterSpec { name: string; bits: number; lanes: number[] /* lane widths offered, e.g. [8,32,64] */ }
interface RegisterFileSpec { isa: string; byteOrder: 'little' | 'big'; registers: RegisterSpec[] }
interface RegisterWrite { reg: string; bytes: number[] /* memory order, byte 0 = lowest address */; valueRef?: string }
interface RegistersFacet {
  kind: 'registers'; schemaVersion: 1; label: I18nRef;
  file: RegisterFileSpec;            // only registers the listing uses; no hardcoded xmm/v lanes in core
  steps: { align: AlignSpan; writes: RegisterWrite[] }[];
}
function registersAt(facet, p): Map<string, number[] | undefined>; // replay of steps with last ≤ p
```

### 3d. `memory`

```ts
interface TargetSpec { triple: string; dataModel: 'LP64' | 'LLP64' | 'ILP32'; ptrSize: number; endian: 'little' | 'big' }
interface LayoutField {
  name: string; offset: number; size: number; type: string;       // C type as printed
  count?: number; elemSize?: number;
  encoding?: 'host-endian-u32' | 'raw-bytes' | 'int';
}
interface StructLayout {
  name: string; impl: string; triple: string; size: number; align: number;
  source: { lib: string; version: string; path: string; line: number };
  fields: LayoutField[];                 // padding = the gaps (views hatch them)
}
interface Allocation {
  id: string; space: 'stack' | 'heap' | 'data' | 'rodata' | (string & {});
  addr: string; size: number; align: number; label: I18nRef;
  layout?: StructLayout; valueRef?: string;
  refs?: { offset: number; size: number; valueRef: string }[];   // e.g. rd_key[4r..4r+3] → round key r
  allocatedAt: number; freedAt?: number;   // state steps
}
interface MemoryWrite { align: AlignSpan; addr: string; bytes: number[]; valueRef?: string }
interface MemoryFacet {
  kind: 'memory'; schemaVersion: 1; label: I18nRef;
  provenance: 'modeled' | 'recorded';
  target: TargetSpec; impl?: { id: string; label: I18nRef };
  allocations: Allocation[]; writes: MemoryWrite[];
}
function memoryAt(facet, p): Map<allocationId, (number | undefined)[]>;  // undefined = never written
```

- Validation:
  - allocations don't overlap;
  - every write lies inside one allocation;
  - field ranges fit the layout's `size`, sorted, and don't overlap;
  - spans are monotonic.

### 3e. `field` (GF(2¹²⁸) terms, for GHASH)

The math facet's `MathTerm.width` is ≤ 32 and stays unchanged. 128-bit field elements get their
own facet:

```ts
interface FieldTerm {
  id: string; label: I18nRef; bytes: number[];   // 16 bytes
  role: MathTermRole; op?: MathOp | 'select';
  bits?: number[];          // emphasised bits in GCM order: 0 = MSB of byte 0 = coefficient of x⁰
  valueRef?: string;
}
interface FieldFacet {
  kind: 'field'; schemaVersion: 1;
  notation: { field: 'gf2^128'; modulus: 'x^128+x^7+x^2+x+1'; bitOrder: 'gcm-reflected' };
  steps: { step: number; formula: I18nRef; terms: FieldTerm[] }[];   // like MathFacet.steps
}
```

- The `mode-chain` and `wire` views render unknown kinds and roles generically. They get styles for

## 4. Memory / ABI

- **Triples:** `x86_64-linux-gnu` and `aarch64-linux-gnu` only, both LP64 and little-endian. The
  riscv64 and Windows (LLP64 probe struct) triples are deferred.
- **Targets are data** in `derivers/src/memory/data/targets.json`.
- **`AES_KEY` (OpenSSL `include/openssl/aes.h`):**
  - `struct aes_key_st { unsigned int rd_key[4*(AES_MAXNR+1)]; int rounds; }`, with
    `AES_MAXNR = 14`. That gives 240 + 4 = **244 bytes, align 4**.
  - **Verify `AES_LONG` is not defined** on these targets. With `AES_LONG` the `rd_key` words
    would be `unsigned long`.
- **Layout data:**
  - `derivers/src/memory/data/layouts/aes_key.<triple>.json` is generated by a dev-only script
    `packages/tools/src/layouts/` with `clang -target <triple> -Xclang -fdump-record-layouts`.
    The compiler version is recorded in the file.
  - CI only checks the committed JSON. A hand-written test asserts size 244, align 4, `rounds` at
    offset 240.
- **Impl × triple** (`derivers/src/memory/data/impls.json`):

  | impl | Triples | `rd_key` encoding | `rounds` field |
  |---|---|---|---|
  | `c-ref` (`crypto/aes/aes_core.c`, `GETU32`) | both | `host-endian-u32` | 10/12/14 |
  | `aesni` (`crypto/aes/asm/aesni-x86_64.pl`) | x86_64 | `raw-bytes` | **verify** (expected 9/11/13) |
  | `armv8` (`crypto/aes/asm/aesv8-armx.pl`) | aarch64 | `raw-bytes` | **verify** (expected 10/12/14) |

  - `host-endian-u32` reverses every 4-byte word in RAM on these little-endian targets.
  - **Pin one OpenSSL tag** (e.g. `openssl-3.5.0`) and record path + line for every claim.
- **`bind(layout, impl, roundKeys, rounds) → bytes`:**
  - It is hand-verified. The test hard-codes the first 16 bytes of `rd_key` for the FIPS 197 A.1
    key under both encodings, e.g. c-ref word `2b7e1516` is stored as `16 15 7e 2b`, and the
    `rounds` bytes.
- **Modelled program:**
  - one stack frame: `unsigned char in[16], out[16]; AES_KEY key;`
  - deterministic, clearly labelled **modeled** addresses (x86_64 `0x7ffc…`, aarch64 `0xffff…`);
  - **writes:**
    - `in` initially;
    - `key` at the `keyExpansion` step (`AES_set_encrypt_key`), with `refs` per round key →
      the `values` subkey ids;
    - `out` at the `output` step.
  - Zeroization and lifetimes are Phase 8.

## 5. ISA derivers and precomputed assembly

- **Source of truth for the instruction list:** the precomputed listings.
  `packages/tools/src/asm/` (dev-only) compiles
  `aes_encrypt_block_{128,192,256}(const uint8_t *in, uint8_t *out, const AES_KEY *key)`.
  - x86 is written with `_mm_aesenc_si128`/`_mm_aesenclast_si128`, ARM with
    `vaeseq_u8`/`vaesmcq_u8`/`veorq_u8`.
  - It runs pinned clang at `-O2`:
    - x86: `-target x86_64-linux-gnu -maes -masm=intel`
    - ARM: `-target aarch64-linux-gnu -march=armv8-a+crypto`
  - It writes `derivers/src/isa-*/data/aes<bits>.json`: `{ compiler, flags, triple, function,
    source, compilerExplorerUrl, instructions: [{ address, mnemonic, operands, role, round? }] }`.
    `role` ∈ `loadState | loadKey | ark0 | round | lastRound | finalXor | aesmc | store | other`,
    and it is annotated by the generator from the mnemonics and operands.
  - The JSON is committed. The local compiler is Homebrew clang 23.1.0. Write the exact
    `--version` line into the JSON.
  - `compilerExplorerUrl` is a **link only**: we never call godbolt.
- **Derivers:** they map each listed instruction to an `AlignSpan` (§1e) and read register values
  **from the trace** (`stateAt` of the state facet at `align.last`; round keys from `w`). They
  compute no AES themselves.

  | Deriver | Rounds | Final round | Note |
  |---|---|---|---|
  | `isa-x86` | `pxor k0`, `aesenc k1…k(Nr−1)` (ShiftRows → SubBytes → MixColumns → ⊕k) | `aesenclast` | |
  | `isa-armv8` | `aese k(r−1)` (⊕k → SubBytes/ShiftRows) + `aesmc` | `aese k(Nr−1)`, `eor kNr` | the fusion note goes on `aese`/`aesmc` pairs |

- **Register byte order:** a register write holds bytes in memory order, byte 0 = lane 0. The
  `registers` view offers "memory order" and "register notation (MSB first)". This is PLAN's
  endianness flip toggle.
- **Tests (PLAN §8):**
  - x86: `xmm` after `aesenc` round r equals FIPS 197 App. C `round[r+1].start` for C.1, C.2 and C.3.
  - ARM: `v` after `aesmc` round r equals App. C `round[r].m_col`.
  - The final register equals the ciphertext.
