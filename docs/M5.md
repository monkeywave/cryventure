# M5 — Hash I (SHA-2): design brief

This is the shared contract for everyone working on M5. The decisions here are binding; record any
deviation in `docs/STATUS.md`. The format follows `docs/M4.md`.

M5 opens PLAN §6 Phase 2a. It has three parts:

- **SHA-2:** producers `sha256` (SHA-224, SHA-256) and `sha512` (SHA-384, SHA-512, SHA-512/224,
  SHA-512/256), a constants producer `sha2-constants`, and the additive `Hash` port.
- **Hardware, second deriver family:** derivers `isa-x86-sha` (Intel SHA extensions, "SHA-NI") and
  `isa-armv8-sha` (ARMv8 SHA2). They reuse the M4 deriver contract, the `instructions`/`registers`
  facets and views, and the M4 asm generator. This proves the deriver contract generalises beyond
  AES.
- **Lessons** `hash/{index,sha256,sha512}`, EN then DE.

## 1. The `Hash` port

A port is resolved by producer id (M3 §1), and a producer exposes one value per port. Hash
functions come in families that share one compression function and differ only in IV and
truncation (SHA-224/256; SHA-384/512/512-t; later SHA3-224…512, SHAKE, BLAKE2s/b). So the port
value is a **family**:

```ts
/** One hash function, untraced. */
export interface HashFunction {
  readonly id: string;          // 'sha-256', 'sha-512/256' (FIPS 180-4 names, lowercase)
  readonly blockSize: number;   // bytes: 64 or 128 (HMAC needs it, RFC 2104 §2)
  readonly outputSize: number;  // bytes: 28, 32, 48, 64
  hash(data: Uint8Array): Uint8Array;
}
/** The functions one producer offers (e.g. `sha512`: sha-384, sha-512, sha-512/224, sha-512/256). */
export interface HashFamily {
  readonly id: string;          // the producer id
  readonly functions: readonly HashFunction[];
}
export interface PortMap { BlockCipher: BlockCipher; Hash: HashFamily }
export function hashFunction(family: HashFamily, id: string): HashFunction | undefined;
```

- A later consumer (HMAC, HKDF; Phase 2b) declares a `port` param `hash` (port `Hash`) plus a
  `select` param for the function id, and fails the run with its own error when
  `hashFunction(...)` is `undefined`. M5 has no consumer; the contract kit tests the port.
- **Tools:** `PORT_SANITY.Hash` in `tools/src/contracts/portChecks.ts`: the family id equals the
  producer id; function ids are unique; every function is deterministic, returns `outputSize`
  bytes for inputs of 0, 1 and `blockSize` bytes, and `blockSize ∈ {64, 128}` for SHA-2.
- `sha256` and `sha512` set `implements: ['Hash']` and export `ports.Hash` built from the
  untraced reference (§2a).

## 2. SHA-2 producers

### 2a. Untraced reference (primitives plugin lib)

`packages/primitives/src/_lib/sha2/` (no manifest; the ESLint `plugin-lib` element from M4 allows
it; it imports core only):

- `sha256Compress(h: Uint32Array, block)`, `sha512Compress(h: BigUint64Array, block)` with 64-bit
  words as `bigint`;
- padding per FIPS 180-4 §5.1.1 (64-bit length) and §5.1.2 (128-bit length);
- the IVs (§5.3.2–5.3.6) and constants (§4.2.2, §4.2.3) as data, plus
  `sha512tIv(t)` (§5.3.6: SHA-512 with IV `H(0) ⊕ a5a5…a5` over the ASCII string `"SHA-512/t"`);
- `SHA2_FUNCTIONS`: the six `HashFunction`s.

Tests: FIPS 180-4 / NIST "Examples with intermediate values" digests for all six functions
(one-block and multi-block messages), and `sha512tIv(224)`/`(256)` equal the §5.3.6.1/§5.3.6.2
IVs. These are the only places outside the oracles where SHA-2 is computed untraced.

### 2b. Params (both producers)

| Param | Kind | Notes |
|---|---|---|
| `algorithm` | select | `sha256`: `sha-224`, `sha-256`. `sha512`: `sha-384`, `sha-512`, `sha-512/224`, `sha-512/256`, `sha-512/t-iv` (see below) |
| `encoding` | select | `utf8` \| `hex` |
| `input` | text | the message; ≤ 128 bytes after decoding (`maxLength` 128); may be empty |
| `detail` | select | `round` (default) \| `block` |

- Validation: `hex` must be an even number of hex digits (empty allowed); read locally in the
  plugin if core's helpers cannot express length 0 (not a core change).
- **`sha-512/t-iv`** is the *IV generation function* of FIPS 180-4 §5.3.6: SHA-512 with the IV
  `H(0) ⊕ a5a5a5a5a5a5a5a5` per word and no truncation. Hashing the text `SHA-512/256` with it
  yields the SHA-512/256 IV. This is how the lessons derive the 512/t IVs ("why these constants")
  without a separate producer.
- 128 bytes means at most 3 SHA-256 blocks and 2 SHA-512 blocks.
- **As built:** `maxLength` is 128 for both encodings. The lab's param panel counts hex-decoded bytes
  when the producer has a sibling `encoding` param set to `'hex'` (`textFieldLength` in
  `apps/web/src/labs/paramFields.ts`; EXTENDING "Text params"), so the limit is the same number of
  message bytes in either encoding.
- **Shared manifest parts:** encodings, detail levels, op names, param fields, presets and
  validation live in `packages/primitives/src/_lib/sha2/manifestKit.ts`. Manifests load eagerly, so
  this file imports `@cryventure/core` only; ESLint allows manifests to import
  `_lib/*/manifestKit.ts`, like the derivers' `_lib/applicability.ts`. The recorder stays behind
  `load()`.

### 2c. Ops, steps and scope

Scope levels: `block → op`. `pad` sits in block 0's scope and `output` in the last block's scope,
so every step has a block. Narration names the algorithm by its FIPS name from the catalog, not
`id.toUpperCase()`.

| Op | Detail | Does |
|---|---|---|
| `pad` | both | message → padded message (§5.1); once, before block 0 |
| `init` | both | H ← IV (once); per block a, …, h ← H |
| `schedule` | round | W_t for t ≥ 16 (§6.2.2 step 1 / §6.4.2 step 1) |
| `round` | round | one compression round t (step 3) |
| `compress` | block | all rounds of one block in one step |
| `feedForward` | both | H ← H + (a, …, h) word-wise (step 4) |
| `output` | both | digest = H, truncated to `outputSize` (§6.3, §6.5–6.7) |

- **Order inside a block at `round` detail:** W_0…W_15 are written by `init` (loaded from the
  block); then for t = 0 … N−1: `schedule t` (only for t ≥ 16), then `round t`. FIPS lists the
  schedule first; computing W_t right before round t gives the same values (W_t depends only on
  earlier words) and is what hardware and most implementations do. The lesson says so. This order
  also keeps derived ISA spans monotonic (§5).
- N = 64 (SHA-224/256) or 80 (SHA-384/512/t). One SHA-512 block at round detail is about
  1 + 64 + 80 + 1 = 146 steps.

### 2d. Facets

- **`state`**, all regions `u8` with a `words` layout (`wordBytes` 4 or 8) in **big-endian byte
  order** as FIPS writes the words. `u64` is not usable (capped at `Number.MAX_SAFE_INTEGER`).
  - `message` (the input; **no** `words` layout, because its length is arbitrary; the region is
    omitted when the message is empty), `padded` (the padded message),
    `w` (the schedule: 64 × 4 or 80 × 8 bytes, `labelPrefix` `W`; per block, rewritten),
    `vars` (a … h, 8 words), `h` (the chaining value H, 8 words), `digest` (`outputSize`
    bytes, blank until `output`).
- **`values`:** `message` (role `public`: a hash input is not a plaintext), `iv` (`constant`, =
  H(0)), `h/1` … `h/N` (the chaining value after block 1 … N, `public`), `digest` (`public`). The IV
  generation function (`sha-512/t-iv`) labels `iv` as H(0)″ (the IV ⊕ a5…a5).
- **`narration`** per step.
- **`wordops`** (§3) at `round` detail: one step per `schedule` and `round` step, plus `init`
  and `feedForward`:
  - `round t` terms: `Σ1(e)`, `Ch(e,f,g)`, `K_t`, `W_t`, **`K_t + W_t`**, `T1`, `Σ0(a)`,
    `Maj(a,b,c)`, `T2`, and the registers a … h before and after;
  - `schedule t` terms: `σ1(W_{t−2})`, `W_{t−7}`, `σ0(W_{t−15})`, `W_{t−16}`, the partial sums
    **`p1 = W_{t−16} + σ0(W_{t−15})`** and **`p2 = p1 + W_{t−7}`**, and `W_t`.
  - `K_t + W_t`, `p1` and `p2` are the lane values that SHA-NI and ARMv8 SHA2 hold in registers
    (`sha256msg1`/`sha256su0` = p1). Emitting them lets the derivers read every register value
    from the trace (§5).
  - `init` and `feedForward` steps carry terms (the loaded/added words) but **no** `registers`;
    registers appear only on `round` (and `compress`) steps.
- **`wordops` at `block` detail** too: one step each for `init`, `compress` and `feedForward`.
  `compress` carries `registers` (a … h before and after all rounds) and no terms.
- **Outputs:** `{ digest }`.

### 2e. Presets

- `sha256`: FIPS 180-4 examples `abc` (SHA-256, the default) and the 56-byte two-block message
  `abcdbcdecdefdefgefghfghighijhijkijkljklmklmnlmnomnopnopq`; SHA-224 `abc`; the empty message.
- `sha512`: SHA-512 `abc` (default) and the 112-byte two-block message; SHA-384 `abc`;
  SHA-512/224 `abc`; SHA-512/256 `abc`; IV generation for `SHA-512/256` and `SHA-512/224`
  (`sha-512/t-iv`).
- **Added during the work:** `sha-256-three-block` (a 3-block message, round detail) and
  `sha-256-two-block-blocks` (the 56-byte message at `block` detail; used by `hash/index`).

### 2f. Conformance and oracles

- `vectors/conformance.json` per producer: the FIPS 180-4 / NIST CSRC "Examples with
  intermediate values" digests for every preset message and algorithm, plus the §5.3.6 IVs as the
  digest of the IV-generation presets. Record the source URLs in `source`.
- **Intermediate values:** a plugin test checks the a … h working variables after rounds t = 0, 1,
  15, 16 and N−1 of the NIST `abc` examples for SHA-256 and SHA-512, transcribed from the NIST
  example PDFs (SHA-256 `abc` t = 0: `5d6aebcd 6a09e667 bb67ae85 3c6ef372 fa2a4622 510e527f
  9b05688c 1f83d9ab`; t = 63: `506e3058 d39a2165 04d24d6c b85e2ce9 5ef50f24 fb121210 948d25b6
  961f4894`), and the W_t of the first block for t = 16 and 63.
- **CAVP:** `vectors/cavp-shortmsg.json`, a filtered copy of the SHAVS byte-oriented
  `SHA{224,256,384,512,512_224,512_256}ShortMsg.rsp` (messages ≤ 128 bytes). Record the source,
  filter and counts in the file. A plugin test runs every case.
- **Oracles** (`tools/src/oracles/sha2.oracle.test.ts`): fast-check against `@noble/hashes`
  (`sha224`, `sha256`, `sha384`, `sha512`, `sha512_224`, `sha512_256`) for random messages of
  0–128 bytes, both through `run()` and through `ports.Hash`. `@noble/hashes` is a root
  devDependency (MIT; add it to `THIRD_PARTY_NOTICES.md`).

### 2g. `sha2-constants` ("why these constants")

A small producer like `aes-sbox`. It computes, with exact `bigint` integer roots (no floating
point), the first w bits of the fractional part of √p or ∛p for the i-th primes:

| Constant | Root | Primes | Bits | FIPS 180-4 |
|---|---|---|---|---|
| SHA-256 `K` | ∛ | first 64 | 32 | §4.2.2 |
| SHA-512 `K` | ∛ | first 80 | 64 | §4.2.3 |
| SHA-256 IV | √ | first 8 | 32 | §5.3.3 |
| SHA-512 IV | √ | first 8 | 64 | §5.3.5 |
| SHA-384 IV | √ | 9th–16th | 64 | §5.3.4 |
| SHA-224 IV | √ | 9th–16th | the **second** 32 bits (the low half of the SHA-384 IV words) | §5.3.2 (values only) |

- Params: `constant` (select of the six rows). Steps: one per word (prime p, ⌊root(p)⌋, the
  fractional bits), then `compare` (equals the FIPS table). Facets `state` (region `constants`,
  `words` layout), `values`, `narration`, `wordops` (terms: p, integer part, fraction word).
- **SHA-224 IV, as verified:** FIPS 180-4 §5.3.2 gives the values only and states no derivation;
  RFC 3874 and RFC 6234 also give values only. The lessons present "the low halves of the SHA-384 IV
  words" as a verifiable observation (the producer checks it), not as the standard's definition.
- The SHA-512/t IVs are not computed here; they come from the `sha512` `sha-512/t-iv` presets
  (§2b).
- Conformance: every row reproduces the FIPS table (as the `constants` output). Test the integer
  root against small hand cases (∛8 = 2, √2 · 2³² ≈ `6a09e667` …).

### 2h. Length extension: no lab

The user decided that attack labs need their explicit go-ahead (2026-10-03). M5 plans **no**
length-extension lab. The lessons cover it conceptually and historically:

- Merkle–Damgård: the digest of SHA-256 and SHA-512 *is* the full chaining value, so `H(m)`
  lets anyone continue hashing from that state; therefore `H(key ‖ m)` is not a MAC. Conceptual,
  with no forging procedure.
- Truncated variants (SHA-384, SHA-512/224, SHA-512/256) do not output the full state; SHA-224
  withholds only 32 bits.
- History by name: Duong & Rizzo, "Flickr's API Signature Forgery Vulnerability" (2009).
- The fix is HMAC (RFC 2104), which comes in Phase 2b.

## 3. Facet schema `wordops` (wave 1)

The `math` facet is 8-bit-field specific (`notation.field: 'gf2^8'`, `width ≤ 32`, `value:
number`), so 32/64-bit word operations get their own facet. It is generic for later ARX and
Boolean-function designs (SHA-1, MD5, BLAKE2, ChaCha). Words are lowercase big-endian hex strings,
so 64-bit values never pass through `number`.

```ts
type WordOp = 'rotr' | 'rotl' | 'shr' | 'xor' | 'and' | 'not' | 'add' | 'ch' | 'maj'
            | 'Sigma0' | 'Sigma1' | 'sigma0' | 'sigma1' | 'root';
interface WordTerm {
  id: string;                 // stable within the step, e.g. 'Sigma1', 'T1', 'p1'
  label: I18nRef;
  hex: string;                // exactly wordBits / 4 lowercase hex digits
  role: MathTermRole;         // reuse: operand | intermediate | constant | carry | result
  op?: WordOp;
  valueRef?: string;
}
interface WordopsFacet {
  kind: 'wordops'; schemaVersion: 1;
  wordBits: 32 | 64;
  registerNames?: string[];   // e.g. ['a', …, 'h']
  steps: {
    step: number;             // state step index, strictly increasing
    formula: I18nRef;
    terms: WordTerm[];
    registers?: { before: string[]; after: string[] };   // hex, length = registerNames.length
  }[];
}
function validateWordopsFacet(facet, stepCount?): string[];
```

Validation: `wordBits` ∈ {32, 64}; every `hex` has `wordBits / 4` lowercase digits; term ids
unique per step; steps strictly increasing and in range when `stepCount` is given; `registers`
only with `registerNames`, both arrays of that length; refs are well-formed `I18nRef`s.

The contract kit (tools) validates `wordops` like the other facets (primitive and deriver
contracts, view fixtures).

## 5. SHA hardware derivers

### 5a. Scope

| Deriver | Variant | Extension | Instructions |
|---|---|---|---|
| `isa-x86-sha` | `x86_64-sha-ni` | Intel SHA extensions | `sha256rnds2` (2 rounds, W+K in implicit `xmm0`), `sha256msg1`, `sha256msg2`, plus `pshufb`/`pshufd`/`palignr`/`pblendw`/`paddd`/loads/stores |
| `isa-armv8-sha` | `aarch64-armv8-sha2` | ARMv8 SHA2 (FEAT_SHA256) | `sha256h`, `sha256h2` (4 rounds each), `sha256su0`, `sha256su1`, plus `rev32`/`add`/`mov`/loads/stores |

- Both apply to `producer.id === 'sha256' && params.detail === 'round'` (SHA-224 and SHA-256 share
  the compression function). `from: ['state', 'values', 'wordops']`.
- **SHA-512 hardware is deferred** (x86 `SHA512` extension `vsha512rnds2`…, ARMv8.2
  `sha512h`/`sha512h2`/`sha512su0`/`sha512su1`); record it in the STATUS backlog for Hash II.
- The memory deriver does not gain `SHA256_CTX` in M5 (backlog).

### 5b. Listings (reuse the M4 asm generator)

- Generalise `packages/tools/src/asm/` from the hard-coded AES `KEY_BITS`/function names to a
  **kernel table**: `{ kernel: 'aes' | 'sha256', sources per ISA, functions, output file,
  annotator }`. The AES listings must regenerate **byte-identical** (a test or a `git diff` check
  in the wave).
- Source: `void sha256_compress_block(uint32_t state[8], const uint8_t block[64])`, one block,
  fully unrolled with macros (straight-line code), `state` as host-endian words like OpenSSL's
  `SHA256_CTX.h`.
  - x86: `_mm_sha256rnds2_epu32`, `_mm_sha256msg1_epu32`, `_mm_sha256msg2_epu32`, following the
    structure of Intel's white paper (Gulley et al., "Intel SHA Extensions", 2013: state packed
    as ABEF/CDGH). Flags `-O2 -msha -mssse3 -msse4.1 -masm=intel -ffreestanding`.
  - ARM: `vsha256hq_u32`, `vsha256h2q_u32`, `vsha256su0q_u32`, `vsha256su1q_u32`. Flags
    `-O2 -march=armv8-a+sha2 -ffreestanding`.
  - Pinned clang 23.1.0 (`/opt/homebrew/opt/llvm/bin`); the `--version` line goes into the JSON.
- Output: `packages/derivers/src/isa-{x86,armv8}-sha/data/sha256.json` in the M4 `Listing` shape.
  Roles (a separate SHA role set, not mixed into the AES `ListingRole`): `loadState`,
  `packState`, `loadBlock`, `byteSwap`, `addK`, `rounds`, `rounds2` (ARM `sha256h2`), `msg1`,
  `msg2`, `unpackState`, `feedForward`, `store`, `other`, with `round` (the first round of the
  instruction) or `w` (the first schedule word it produces).
- The annotator assigns rounds and schedule words by the mnemonic's occurrence order (round
  instructions in order of t; message instructions in order of the words they produce), and a
  test checks the counts (x86: 32 `sha256rnds2`, 12 `msg1`, 12 `msg2`; ARM: 16 `sha256h`,
  16 `sha256h2`, 12 `sha256su0`, 12 `sha256su1`).
- **Verification as built:** the ARM listing was verified natively on an M1. The x86 SHA-NI listing
  is verified only against C models of `sha256rnds2`/`sha256msg1`/`sha256msg2` (Rosetta 2 lacks the
  SHA extensions), not on SHA-NI hardware.
- **ARM K constants:** the annotator resolves which K_t a register holds by following the register
  to its `add` with the message register, not by the `.LCPI` constant-pool label.

### 5c. Values: read from the trace, never computed

The M4 rule holds: a deriver computes no hash. Every register value comes from the trace:

- working variables from `vars` (`stateAt` at `align.last`), schedule words from `w`, H from `h`;
- `K_t + W_t`, `p1` and `p2` from the `wordops` facet (§2d);
- derivers may only **rearrange** bytes: byte swaps (`pshufb`, `rev32`), lane order, and the
  ABEF/CDGH packing.
- **Role notes (as built, `tools/src/asm/annotateSha.ts`):** on x86, `pshufd …, 14` (moving the
  upper K+W pair down for the second `sha256rnds2`) is `addK`; `palignr`/`paddd` on schedule words
  are `msg2` without a `w` (they prepare the `sha256msg2` input); a state shuffle after the first
  round instruction counts as `unpackState`, so clang's early one in round 0 is labelled that way.

Multi-block messages repeat the listing per block. Spans (M4 §1e):

| Instruction | `align` |
|---|---|
| `sha256rnds2` for rounds t, t+1 | `round t` … `round t+1` |
| `sha256h` / `sha256h2` for rounds t … t+3 | `round t` … `round t+3` |
| `msg1`/`msg2`/`su0`/`su1`, `addK`, shuffles | zero-width at the **next** round instruction's `first` |
| `loadState`, `packState`, `loadBlock`, `byteSwap` | zero-width at the block's `init` step |
| `feedForward`, `unpackState`, `store` | zero-width at `feedForward` / the `output` step |

Hardware computes schedule words ahead of the round that uses them, so the registers view shows a
message register holding `p1`/`W_t` before the state view writes W_t. That is the teaching point
(the "sliding window" of 16 words), and the instructions view says so in a note.

### 5d. Shared code and tests

- `packages/derivers/src/_lib/sha/` holds the SHA contract reader (`shaTrace`: regions `vars`,
  `w`, `h`, ops `init`/`schedule`/`round`/`feedForward`/`output`, the `wordops` terms) and the
  span builder. Generic parts of `_lib/isaDerivation.ts` (register file spec, facet assembly) may
  be extracted for reuse; the M4 golden fixtures must stay **unchanged**.
- Goldens: `fixtures/sha256-abc.golden.json` for both derivers.
- Tests:
  - x86: ABEF/CDGH after the `sha256rnds2` for rounds t, t+1 equal the NIST `abc` a … h after
    round t+1 (t = 0, 14, 62).
  - ARM: `q0` (ABCD) after `sha256h` and `q1` (EFGH) after `sha256h2` for rounds t … t+3 equal
    a … d / e … h after round t+3.
  - The message register after the last `msg2`/`su1` of a group equals W_t … W_{t+3}.
  - The stored state equals the digest words (SHA-256) and H for a two-block message.
