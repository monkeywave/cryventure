# M6 — Hash II (SHA-3/Keccak, BLAKE2, MD5/SHA-1): design brief

This is the shared contract for everyone working on M6. The decisions here are binding; record any
deviation in `docs/STATUS.md`. The format follows `docs/M5.md`.

M6 finishes PLAN §6 Phase 2a. It has five parts:

- **Sponge:** producer `sha3` (SHA3-224/256/384/512, SHAKE128/256, cSHAKE128/256, Keccak-256) on
  Keccak-f[1600]; a constants producer `keccak-constants` (ι round constants from the LFSR, ρ
  offsets, π); a new `sponge` facet and view.
- **ARX:** producer `blake2` (BLAKE2s/BLAKE2b, RFC 7693, keyed mode) on the `wordops` facet, which
  moves to schema v2.
- **Historical:** producers `md5` and `sha1` (needed in Phase 2b for the TLS 1.0 PRF anyway).
- **Hardware:** ARMv8.2 SHA512 (extends `isa-armv8-sha`) and ARMv8.2 SHA3 (new deriver
  `isa-armv8-sha3`), both verified natively on this Apple M1 (`hw.optional.armv8_2_sha3` and
  `armv8_2_sha512` = 1).
- **The incremental `Hash` port** (init/update/digest, clone = midstate) and an XOF port shape, for
  Phase 2b (HMAC, PBKDF2, KMAC) and Phase 6 (ML-KEM's SHAKE).

Lessons `hash/{md5-sha1,sponge,keccak,blake2}` are new; `hash/{index,sha512}` are updated. EN first,
then DE.

**Not in M6:** attack labs (user rule, see §9); x86 SHA512 (`vsha512rnds2`, no hardware to verify
it on, Rosetta lacks it) and SHA-1 hardware (`sha1rnds4`, `sha1c`…); BLAKE2 salt/personalization;
BLAKE3; KangarooTwelve/TurboSHAKE; `SHA256_CTX` in the memory deriver; 32-bit hi/lo references for
64-bit words (stay on the backlog for PBKDF2 in 2b, see §2a).

## 0. Core-diff budget

Core changes only in **wave 1**, in two commits:

1. **`wip(m6): incremental Hash port + XOF`** (§1): `core/src/ports.ts` (+ tests), plus the minimum
   outside core that keeps the gates green: the existing implementers (`_lib/sha2` gains contexts)
   and `PORT_SANITY.Hash` in tools. Nothing else.
2. **`wip(m6): sponge facet, wordops v2, words byteOrder, latestStepAt`** (§3): facet schemas and
   validators, their exports from `core/src/index.ts`, `'sponge'` in `KnownFacetKind`, and the
   generic `latestStepAt` (§3d). Replacing the views' copy of `latestStepAt` happens in wave 3.

**The proof:** from commit 2 on, `git diff <commit 2> -- packages/core` stays **empty** through
producers, derivers, views, lessons, the reviews, `/simplify` and `/code-review`. The final review
checks this. `DeriverManifest`, `ViewManifest`, `PrimitiveManifest`, `viewsFor`, port resolution and
the tracer do **not** change. No reference hash code goes into core (it lives in the primitives'
plugin libs, §2a); oracles use `@noble/hashes` (2.4.0 is installed and has `sha3`, `sha3-addons`,
`blake2`, `legacy`, so M6 installs **nothing**).

## 1. The `Hash` port, incremental, plus XOFs

```ts
/** A running hash computation (init → update* → digest). */
export interface HashContext {
  /** Absorbs more data. */
  update(data: Uint8Array): void;
  /** The digest of everything absorbed so far; does not change the context (it finalises a copy). */
  digest(): Uint8Array;
  /** An independent copy, e.g. the HMAC midstate after the ipad block. */
  clone(): HashContext;
}

export interface HashFunction {
  readonly id: string;          // 'sha-256', 'sha3-256', 'keccak-256', 'blake2s-256', 'md5', 'sha-1'
  readonly blockSize: number;   // bytes: the compression block, or the sponge rate (SHA3-256: 136)
  readonly outputSize: number;
  hash(data: Uint8Array): Uint8Array;
  create(): HashContext;        // new
}

/** SP 800-185 §3.3 function-name string N and customization string S (cSHAKE only). */
export interface XofCustomization {
  readonly functionName?: Uint8Array;
  readonly customization?: Uint8Array;
}
export interface XofContext {
  update(data: Uint8Array): void;      // throws after the first squeeze
  squeeze(length: number): Uint8Array; // the next `length` output bytes
  clone(): XofContext;
}
/** An extendable-output function (FIPS 202 SHAKE, SP 800-185 cSHAKE). */
export interface XofFunction {
  readonly id: string;           // 'shake128', 'shake256', 'cshake128', 'cshake256'
  readonly blockSize: number;    // the rate in bytes: 168 or 136
  readonly securityBits: number; // 128 or 256
  readonly customizable: boolean;
  xof(data: Uint8Array, outputLength: number, custom?: XofCustomization): Uint8Array;
  create(custom?: XofCustomization): XofContext;
}

export interface HashFamily {
  readonly id: string;
  readonly functions: readonly HashFunction[];
  readonly xofs?: readonly XofFunction[];   // new, optional
}
export function xofFunction(family: HashFamily, id: string): XofFunction | undefined;  // new
```

- A non-customizable XOF throws when given a non-empty N or S. cSHAKE with N and S both empty
  equals SHAKE (SP 800-185 §3.3); the port test checks it.
- Contexts are real: they compress whole blocks as data arrives and keep only a partial block, so
  `clone()` after one block is a true midstate. A buffering fallback ("store everything, hash at
  `digest()`") is not allowed.
- **`PORT_SANITY.Hash`** (tools) grows: `blockSize > 0` and `outputSize > 0` (no longer `{64, 128}`);
  for every function, `create()` + `update` over splits (0 | n, 1 | n−1, block-aligned, byte by byte
  for short inputs) equals `hash()`; `digest()` twice gives the same bytes and does not stop
  `update`; a clone is independent of its source. For every XOF: unique ids across functions and
  XOFs; `xof(m, a + b)` = `squeeze(a) ‖ squeeze(b)`; `update` after `squeeze` throws; the
  non-customizable rule above.
- `_lib/sha2` implements `create()` for its six functions in commit 1.

## 2. Producers

### 2a. Plugin libs (untraced references)

All under `packages/primitives/src/_lib/` (no manifest; import core only), each with a
`manifestKit.ts` for the eager manifest parts, as `_lib/sha2` does:

- **`_lib/keccak/`:** Keccak-f[1600] with `bigint` lanes (lane index `x + 5y`, FIPS 202 §3.1.2),
  the five step mappings as separate functions (`theta` also returns C and D), the round constants
  (Keccak reference 3.0 §1.2), ρ offsets (FIPS 202 Table 2) and π map **as data** (§3.2.2–3.2.5), `pad10*1` with the domain
  suffix, the sponge (absorb/squeeze), SP 800-185 `left_encode`/`right_encode`/`encode_string`/
  `bytepad`, and the `HashFunction`/`XofFunction` objects.
- **`_lib/blake2/`:** BLAKE2s (32-bit words, 10 rounds) and BLAKE2b (64-bit, `bigint`, 12 rounds),
  `G`, σ, the IVs, parameter block word 0 (`0x0101kknn`), counter and final flag (RFC 7693 §2–3).
- **`_lib/md5/`** and **`_lib/sha1/`**, or one `_lib/legacy-md/` (agent's choice). SHA-1 reuses the
  `_lib/sha2` padding (FIPS 180-4 §5.1.1); MD5 has its own (little-endian 64-bit length, RFC 1321
  §3.2).
- **Words are `bigint` for 64-bit** (as in M5). A port-speed budget test per family (1 KiB in
  < 1000 ms on CI; generous so it does not flake under load, a few ms is typical, it only catches
  catastrophic regressions) guards against regressions; hi/lo `Uint32Array` stays on the backlog for PBKDF2.

### 2b. `sha3`

**Port:** `implements: ['Hash']`; family `sha3` with functions `sha3-224`, `sha3-256`, `sha3-384`,
`sha3-512`, `keccak-256` and XOFs `shake128`, `shake256`, `cshake128`, `cshake256`.

**Params:**

| Param | Kind | Notes |
|---|---|---|
| `algorithm` | select | the nine ids above |
| `encoding` | select | `utf8` \| `hex` |
| `input` | text | ≤ **200** bytes after decoding (admits the NIST 1600-bit example), may be empty |
| `outputLength` | select | XOFs only: `16`, `32`, `64`, `168`, `336` bytes (168 = one SHAKE128 rate, 336 shows a second squeeze); ignored by the fixed-length functions |
| `functionName` | text | cSHAKE N (UTF-8, ≤ 64 bytes); a non-empty value with another algorithm is a validation error |
| `customization` | text | cSHAKE S (UTF-8, ≤ 64 bytes); same rule |
| `detail` | select | `mapping` (default) \| `round` \| `permutation` |

**Padding and domain separation** (FIPS 202 §6.1–6.2, SP 800-185 §3.3): SHA3 appends `01`, SHAKE
`1111`, cSHAKE `00` after `bytepad(encode_string(N) ‖ encode_string(S), rate)`, Keccak-256 nothing
(the pre-standard Keccak padding, as Ethereum uses). In bytes with pad10*1: `06…80`, `1f…80`,
`04…80`, `01…80`. The narration of `pad` names the suffix.

**Ops and scope** (levels `block → round → op` at `mapping`, `block → op` otherwise; `pad` sits in
block 0's scope, `output` in the last one's):

| Op | Detail | Does |
|---|---|---|
| `pad` | all | message (with the cSHAKE prefix) → padded message; once |
| `absorb` | all | XOR one rate block into lanes `0 … rateLanes−1` |
| `theta`, `rho`, `pi`, `chi`, `iota` | `mapping` | one step mapping of round i (24 rounds) |
| `round` | `round` | one whole round |
| `permute` | `permutation` | all 24 rounds |
| `squeeze` | all | read rate bytes out; repeated (with a permutation before each further block) until `outputLength` |
| `output` | all | digest = the first d bits |

SHA3-256 "abc" at `mapping` detail is about 1 + 1 + 120 + 1 + 1 steps.

**Facets:**

- **`state`:** `message` (omitted when empty), `padded`, `A` (200 bytes in FIPS 202 byte order,
  `words` layout `wordBytes 8`, `byteOrder: 'little'`, §3c), `output` (blank until written).
- **`values`:** `message` (`public`), `n`/`s` for cSHAKE (`public`), `digest` (`public`).
- **`sponge`** (§3a): every step, with `theta: {c, d, partial}` on θ steps and `iota.rc` on ι steps.
  `partial[x] = A[x,0] ⊕ A[x,1] ⊕ A[x,2]` is what a three-input XOR (ARMv8.2 `EOR3`) holds after
  its first step; emitting it lets the SHA3 deriver read every register from the trace (§5).
- **`narration`** per step. **Outputs:** `{ digest }`.

**Presets:** `sha3-256-abc` (default), `sha3-224-abc`, `sha3-384-abc`, `sha3-512-abc`,
`sha3-256-empty` (NIST Msg0), `sha3-256-1600` (200 × `a3`, two blocks), `sha3-256-abc-permutation`
(used by `hash/sponge`), `shake128-abc-336` (two squeezes), `shake256-empty`, `cshake128-sample1`
(SP 800-185 sample #1: data `00010203`, N "", S "Email Signature", 32 bytes), `keccak-256-abc`.

### 2c. `keccak-constants` ("why these constants")

Like `sha2-constants`. Param `constant`: `rc` (default) | `rho`.

- **`rc`:** the ι constants from the LFSR `rc(t)` = coefficient of x⁰ in `x^t mod (x⁸ + x⁶ + x⁵ +
  x⁴ + 1)` over GF(2) (FIPS 202 Algorithm 5); `RC[i]` has bit `2^j − 1` = `rc(j + 7i)` for
  j = 0…6 (Algorithm 6). One step per round i (the seven LFSR bits and the assembled RC word),
  then `compare` (equals the `_lib/keccak` table; FIPS 202 does not print RC, so the source is the Keccak reference 3.0 §1.2 — FIPS 202 Table 2 is the ρ offsets). Facets: `state` (region
  `lfsr`, 1 byte; region `rc`, 24 × 8 bytes, `words` layout), `values`, `narration`, `wordops`
  (64-bit; terms: the LFSR output bits as `rc(…)` words, RC[i] as the result).
- **`rho`:** the walk `(x, y) ← (y, 2x + 3y mod 5)` from (1, 0), t = 0…23, offset `(t+1)(t+2)/2
  mod 64` (FIPS 202 Algorithm 2). One step per t. Region `offsets`: `u8`, shape `[5, 5]`,
  row-major so the cell index is `x + 5y`, blank until written. The narration makes the two points
  explicit: the matrix `[[0,1],[2,3]]` visits all 24 non-zero positions, and the triangular numbers
  give 24 distinct offsets mod 64. π's map `A'[x,y] = A[(x + 3y) mod 5, x]` is shown in the `sponge`
  view, not here.
- Conformance: both reproduce the `_lib/keccak` data (which itself is tested against FIPS 202).

### 2d. `blake2`

**Port:** family `blake2` with `blake2s-128`, `blake2s-160`, `blake2s-224`, `blake2s-256`,
`blake2b-160`, `blake2b-256`, `blake2b-384`, `blake2b-512` (RFC 7693 §4), unkeyed. Keyed BLAKE2 as
a MAC is Phase 2b's `Mac` port.

**Params:** `algorithm` (the eight ids), `encoding`, `input` (≤ 128 bytes), `key` (hex, 0…32 bytes
for BLAKE2s and 0…64 for BLAKE2b, empty = unkeyed), `detail` `g` (default) | `round` | `block`.

**Ops** (`block → round → op` at `g` detail): `init` (h ← IV ⊕ parameter word 0), `load` per block
(v[0..7] ← h, v[8..15] ← IV, `v12 ^= t0`, `v13 ^= t1`, `v14 ^= ~0` on the last block), `g` (one
G call: i = 0…3 columns, 4…7 diagonals), `round` / `compress` at the coarser details,
`feedForward` (h ← h ⊕ v[0..7] ⊕ v[8..15]), `output`. A key becomes block 0 (zero-padded,
RFC 7693 §3.3). The empty unkeyed message compresses one all-zero block.

**Facets:**

- **`state`:** `message`, `key` (when keyed), `m` (the current block as 16 words), `h` (8 words),
  `v` (16 words, `words` layout `wordsPerGroup 4` so it shows as the 4 × 4 matrix), `digest`. All
  words `byteOrder: 'little'` (RFC 7693 §2.4).
- **`wordops` v2** (§3b): `wordBits` 32 or 64, `registerNames` `v0 … v15`, `registerColumns 4`.
  A `g` step's terms, in order: `m[σ(2i)]`, `m[σ(2i+1)]`, then `a1 = a + b + m₀`,
  `d1 = (d ⊕ a1) ⋙ R1`, `c1 = c + d1`, `b1 = (b ⊕ c1) ⋙ R2`, `a2`, `d2`, `c2`, `b2` (R1…R4 = 16, 12,
  8, 7 for BLAKE2s and 32, 24, 16, 63 for BLAKE2b), with `touched` = the four indices and
  `transfers` writing a2/b2/c2/d2. `emphasis: 'story'` on a2, b2, c2, d2. `init`, `load`,
  `feedForward` carry terms but no registers.
- **`values`:** `message`, `key` (role `key`), `iv` (`constant`), `h/1…h/N`, `digest`.

**Presets:** `blake2s-256-abc` (default; RFC 7693 Appendix B), `blake2b-512-abc` (Appendix A),
`blake2s-256-empty`, `blake2s-256-keyed` (key `00…1f`, message `00 01 02`, from the reference KAT),
`blake2b-512-abc-round` (round detail).

**"Why these constants":** the BLAKE2 IVs are the SHA-256/SHA-512 IVs (√ of the first 8 primes),
which the lesson shows next to `sha2-constants`; σ is BLAKE's (and ChaCha's lineage).

### 2e. `md5` and `sha1`

Two producers, M5 shape (params `encoding`, `input` ≤ 128 bytes, `detail` `round` | `block`; ops
`pad`, `init`, `schedule` (SHA-1 only, t ≥ 16), `round`, `compress`, `feedForward`, `output`;
scope `block → op`). Ports: family `md5` {`md5`}, family `sha1` {`sha-1`}.

- **MD5** (RFC 1321): registers `a b c d`; words and the length little-endian (`byteOrder:
  'little'`); `round` terms: the round function (`F`=`ch`, `G`=`md5G`, `H`=`parity`, `I`=`md5I`),
  `X[k]`, `T[i]`, the sum, the rotation by `s` (`rotl`), the new b; `transfers` a ← d, c ← b,
  d ← c, b ← new. T[i] = ⌊2³² · |sin(i)|⌋ is shown in the lesson (prose plus a lib test against the
  RFC table), not as a producer.
- **SHA-1** (FIPS 180-4 §6.1): registers `a … e`; schedule `W_t = ROTL¹(W_{t−3} ⊕ W_{t−8} ⊕
  W_{t−14} ⊕ W_{t−16})`; `round` terms `ROTL⁵(a)`, `f_t` (`ch` / `parity` / `maj`), `e`, `K_t`,
  `W_t`, `T`; `transfers` e ← d, d ← c, c ← ROTL³⁰(b) (a term), b ← a, a ← T. K are
  ⌊2³⁰ · √2, √3, √5, √10⌋ (prose plus a lib test).
- Regions as SHA-2 (`message`, `padded`, `w` for SHA-1, `vars`, `h`, `digest`).
- **Presets:** `md5-abc` (default), `md5-empty`, `md5-digits` (RFC 1321's 80 digits, two blocks);
  `sha1-abc` (default), `sha1-two-block` (the 56-byte message), `sha1-empty`.

### 2f. SHA-2 producers (changes)

- Emit **`wordops` v2** (§3b): `transfers` for the register shift (b ← a, …, e ← d + T1 as a term,
  a ← T1 + T2 as a term), `emphasis: 'story'` on T1 and T2; `sha2-constants` sets `degree` 2 or 3 on
  its `root` terms.
- `sha512` `round` gains term **`hKW` = h + K_t + W_t** (the input of ARMv8.2 `SHA512H`; g + K + W of
  the next round is that round's `hKW`). Ids of existing terms do not change.
- Regenerate bundle fixtures and goldens; the M5 derivers' goldens may change only by the v2 fields.

## 3. Facet schemas (wave 1, commit 2)

### 3a. `sponge` (new)

```ts
export type SpongePhase = 'pad' | 'absorb' | 'theta' | 'rho' | 'pi' | 'chi' | 'iota' | 'round'
                        | 'permute' | 'squeeze' | 'output';
export interface SpongeStep {
  step: number;                // state step index, strictly increasing
  phase: SpongePhase;
  round?: number;              // 0 … rounds−1 for the round phases
  lanes: string[];             // width·height lanes after the step, lane integers as laneBits/4 hex digits (MSB first)
  input?: string[];            // absorb: the rateLanes lanes XORed in
  output?: string;             // squeeze/output: the bytes read out, hex in byte order
  theta?: { c: string[]; d: string[]; partial?: string[] };   // width entries each
  iota?: { rc: string };
}
export interface SpongeFacet {
  kind: 'sponge'; schemaVersion: 1;
  label: I18nRef;              // 'Keccak-f[1600]'
  width: number; height: number;   // 5 × 5; lane index = x + width·y
  laneBits: 8 | 16 | 32 | 64;
  rounds: number;              // 24
  rateLanes: number;           // lanes 0 … rateLanes−1 (index order) are the rate, the rest the capacity
  rhoOffsets?: number[];       // per lane index: left-rotation amount
  piSource?: number[];         // per lane index: after π, lane i holds what lane piSource[i] held
  steps: SpongeStep[];
}
export function validateSpongeFacet(facet: unknown, stepCount?: number): string[];
```

Validation never throws: shape fields are positive integers; `lanes` has `width·height` entries of
`laneBits/4` lowercase hex digits; `input` has `rateLanes` entries; `theta.*` have `width` entries;
`rhoOffsets` in `[0, laneBits)`; `piSource` a permutation; `round < rounds`; steps strictly
increasing and in range with `stepCount`; `label` a well-formed `I18nRef`. Generic enough for
Ascon (5 × 1 lanes, Phase 3) and Keccak-p[1600, 12].

### 3b. `wordops` schema v2

Additive; `schemaVersion: 1 | 2`, and the new fields are allowed only with 2. All producers emit 2
by the end of wave 2; views keep reading 1.

- `WordOp` adds `'or' | 'parity' | 'md5G' | 'md5I'`.
- `WordTerm` adds `emphasis?: 'story'` (the story lens shows only these terms; without any, it shows
  none) and `degree?: 2 | 3` (only with `op: 'root'`; the view writes √ or ∛).
- `WordopsFacet` adds `registerColumns?: number` (draw the registers as a grid, e.g. 4 for the
  BLAKE2 matrix).
- `WordopsStep.registers` adds `touched?: number[]` (register indices the step reads and writes) and
  `transfers?: { to: number; from: { register: number } | { term: string } }[]`: `after[to]` comes
  from `before[from.register]` or from the term `from.term`. Validation checks indices, unique `to`,
  that the term exists, and that the hex values agree. This replaces the view's structural SHA-2
  shift detection (kept as the fallback for v1 facets).
- `validateWordopsFacet` **never throws** on malformed input (it returns problems), and core exports
  the tables `WORD_OPS` and `WORD_TERM_ROLES` so tools stops duplicating them.

### 3c. `words` layout `byteOrder`

`RegionLayout` `words` gains `byteOrder?: 'big' | 'little'` (default `big`; additive, schemaVersion
stays 1). With `little`, the state view shows each word as its integer value (bytes reversed) and
offers "memory order" in the engineer lens. Used by Keccak lanes, BLAKE2 and MD5.

### 3d. `latestStepAt`

A generic `latestStepAt(steps, playhead)` (the last item whose `step ≤ playhead`, by binary search)
in core with tests. Wave 3 replaces the copy in `views/_lib` and any other copies (callers keep their
behaviour; check each for differences first).

### 5a. Scope

### 5b. Listings (asm generator kernel table)

- New kernels in `packages/tools/src/asm/`, pinned clang 23.1.0, `--version` line in the JSON; AES
  and SHA-256 listings regenerate **byte-identically**.
  - `sha512_armv8.c`: `void sha512_compress_block(uint64_t state[8], const uint8_t block[128])`,
    unrolled, `vsha512hq_u64`/`vsha512h2q_u64`/`vsha512su0q_u64`/`vsha512su1q_u64`, flags
    `-O2 -march=armv8.2-a+sha3 -ffreestanding` (LLVM puts FEAT_SHA512 under `+sha3`). Structure as
    Linux `arch/arm64/crypto/sha512-ce-core.S` (state in four q registers as (a,b), (c,d), (e,f),
    (g,h)). Expected counts: 40 `sha512h`, 40 `sha512h2`, 32 `sha512su0`, 32 `sha512su1`.
  - `keccak_armv8.c`: `void keccak_f1600(uint64_t A[25])` with the lanes in the low halves of 25
    vector registers, one round per loop iteration (`#pragma clang loop unroll(disable)`), RC from
    a table, `veor3q_u64`, `vrax1q_u64`, `vxarq_u64`, `vbcaxq_u64`; θ's column parity written as
    `veor3q_u64(veor3q_u64(a0, a1, a2), a3, a4)` (this fixes what `partial` means). Flags
    `-O2 -march=armv8.2-a+sha3 -ffreestanding`. The listing has a prologue (load), a loop body (one
    round) and an epilogue (store); the deriver repeats the body 24 times per permutation and the
    whole function per permutation. If clang spills, keep the spills (the listing stays honest) and
    give them role `other`. Expected per body: 10 `eor3`, 5 `rax1`, 24 or 25 `xar` (lane (0,0) has
    ρ offset 0 and may become a plain `eor`), 25 `bcax`, one `eor` for ι (or folded; the annotator
    reports what clang did).
- **Roles:** SHA-512 reuses the SHA role set (`loadState`, `packState`, `loadBlock`, `byteSwap`,
  `addK`, `rounds`, `rounds2`, `msg1`, `msg2`, `unpackState`, `feedForward`, `store`, `other`).
  Keccak gets its own set: `loadState`, `loadRc`, `thetaParity` (`eor3`, with `x` and `half: 1 | 2`),
  `thetaD` (`rax1`, `x`), `thetaRhoPi` (`xar`, `lane` = destination after π), `chi` (`bcax`, `lane`),
  `iota`, `loop`, `storeState`, `other`.
- **Verification:** both listings run natively on this M1 against the `_lib` references (a small C
  harness in `tools/src/asm`, run by the asm agent and documented, not in CI).

### 5c. Values: read from the trace, never computed

The M4/M5 rule holds: a deriver only rearranges bytes.

- **SHA-512:** a … h from `vars`, W from `w`, `K_t + W_t`, `hKW`, `T1`, p1/p2 from `wordops`;
  `sha512h` output = (T1_t, T1_{t+1}); `sha512h2` output = the new (a, …) pair; the `add` after
  `sha512h` = the new e pair (all `vars` words). Lane order and `ext` swaps are rearrangements.
- **SHA3:** lanes from `sponge` steps (`absorb`, `theta`, `rho`, `pi`, `chi`, `iota`), C and D and
  `partial` from `theta`, RC from `iota.rc`. `xar` yields the ρ-step lane value, placed in the
  register that holds the π destination; `bcax` yields the χ-step lane; ι's `eor` the ι-step lane.

**Spans** (M4 §1e; never decreasing):

| Instruction | `align` |
|---|---|
| `sha512h` / `sha512h2` for rounds t, t+1 | `round t` … `round t+1` |
| `sha512su0`/`su1`, `addK`, `ext` | zero-width at the next round instruction's `first` |
| `eor3`, `rax1` | the round's `theta` step |
| `xar` | `theta` … `pi` of the round |
| `bcax` | the round's `chi` step |
| ι `eor`, RC load | the round's `iota` step (RC load zero-width at its `first`) |
| loads / `absorb` | zero-width at the `absorb` step; stores at `squeeze`/`output` |
